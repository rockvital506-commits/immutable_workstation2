# Соглашения по наполнению

Документ обязателен к применению для любого нового файла в репозитории.
Проверяется автоматически: `scripts/repo-validate.sh` / `scripts/repo-validate.ps1`.

---

## 1. Именование

| Объект | Правило | Пример |
|--------|---------|--------|
| Каталог | Латиница, `snake_case`, без пробелов | `data_recovery` |
| Каталог-утилита | Имя продукта как есть, латиница | `Victoria`, `Rufus`, `memtest86plus` |
| Служебный файл | Латиница, `kebab-case` | `check-flash.sh`, `unattended-base.xml` |
| ISO | `<Продукт>_<Версия>_<Арх>_<Язык>[_<Дата>].iso` | `Win11_24H2_x64_RU_2026-01.iso` |
| Заглушка | Имя целевого файла + `.md` | `Win11_24H2_x64_RU.iso.md` |

Запрещено: кириллица в именах файлов и каталогов, пробелы, символы
`# % & { } \ < > * ? / $ ! ' " @ + \` =`, имена длиннее 60 символов.

## 2. Правило заглушек (главное правило репозитория)

В git попадают **все текстовые файлы**: конфиги, скрипты, документация, ответы,
манифесты, шаблоны. Бинарные и крупные файлы не попадают — вместо них лежит
текстовая заглушка с суффиксом `.md`.

**Заглушка = исходное имя файла + `.md`.** Не `name.md` вместо `name.exe`,
а именно `name.exe.md` — так заглушка однозначно указывает на оригинал.

Расширения, для которых обязательна заглушка (список синхронизирован с
`repo-validate` и `.gitignore`):

```
.iso .wim .esd .swm .vhd .vhdx .img .vtoy .efi
.exe .msi .msu .dll .sys .com .bat? (bat — текст, хранится как есть)
.zip .7z .rar .gz .xz .bz2 .tar .cab .dat .bin .rom .efi .iso.zst
.pf2 .png .jpg .jpeg .gif .ico .bmp .ttf .otf .woff .woff2
.mp3 .mp4 .mkv .avi .wav .pdf .docx .xlsx
```

> `.bat`, `.cmd`, `.ps1`, `.sh`, `.xml`, `.json`, `.cfg`, `.inf`, `.reg`, `.txt`, `.csv`
> — это текст, хранятся в git **как есть**, без заглушек.

### Шаблон заглушки бинарника

```markdown
# <имя файла>

> **Это заглушка.** Файл `<имя>` в git не хранится.
> Скачайте его по ссылке ниже и положите рядом с этой заглушкой на флешке.

| Поле | Значение |
|------|----------|
| Имя файла | `test.exe` |
| Версия | 1.2.3 |
| Размер | 10 485 760 байт (10,0 МБ) |
| SHA256 | `<64 hex>` |
| Источник | <официальный URL> |
| Лицензия | Freeware / Shareware / GPL / Commercial |
| Добавлено | 2026-10-07 |

## Назначение
Что делает утилита, в каких случаях применяется.

## Запуск
Точная команда или двойной клик, требуемые права (Admin/обычные).

## Проверка подлинности
Команда сверки хэша под Windows и под Linux.
```

## 3. README.md обязателен

`README.md` обязан быть:

- в каждом каталоге-утилите (`tools/**/<Утилита>/README.md`);
- в каждом каталоге-группе и подкатегории (`tools/<Группа>/README.md`);
- в `ventoy-partition/ISO/<категория>/README.md` — что за образы там лежат;
- рядом с каждым ISO в виде `<имя>.iso.md`.

Отсутствие `README.md` в каталоге с заглушкой — ошибка валидации.

### Три шаблона

| Шаблон | Когда применять |
|--------|-----------------|
| `tools/_templates/UTILITY_README.md` | Каталоги сторонних и наших утилит |
| `tools/_templates/SCRIPT_README.md` | Каталоги со скриптами |
| `tools/_templates/MODULE_README.md` | Составные модули (набор утилита + скрипт + инструкция) |

## 4. manifest.csv — единый реестр

Каждый ISO и каждая утилита с бинарником имеют строку в `manifest.csv`.
Формат (первая строка — заголовок, разделитель `,`, кавычки для значений с запятой):

```
type,category,name,file,url,sha256,size_bytes,version,added,status
```

| Поле | Значение |
|------|----------|
| `type` | `iso` \| `tool` \| `script` \| `module` |
| `category` | Путь категории от корня раздела, напр. `ISO/windows` или `diagnostics/disk` |
| `name` | Человекочитаемое имя |
| `file` | Имя файла на флешке. **Пустое** для `type=module` и `type=script`: это не один файл, а каталог или группа скриптов, поэтому состав задаёт таблица `SELF_ENTITIES` в `scripts/csv-check.py` |
| `url` | Официальный источник (пусто для наших наработок) |
| `sha256` | Хэш или `PENDING` |
| `size_bytes` | Размер в байтах или `0` |
| `version` | Версия |
| `added` | Дата добавления `ГГГГ-ММ-ДД` |
| `status` | `planned` \| `present` \| `verified` \| `deprecated` |

Строки со `status=planned` допускают `sha256=PENDING` и `size_bytes=0`.
Для `present`/`verified` оба поля обязательны.

### Правило SELF-HASH для наших сущностей

Для строк `type=module` и `type=script` со `status=present` значение `sha256`
обязано совпадать с хэшем **реальных файлов репозитория**. Хэш считается по
конкатенации файлов сущности в порядке сортировки путей:

```python
digest = hashlib.sha256()
for rel in sorted(files):          # например .ps1 и .sh одной задачи
    digest.update(open(rel, 'rb').read())
```

Состав файлов каждой сущности объявлен в `scripts/csv-check.py`, словарь
`SELF_ENTITIES`. Правило проверяется автоматически: правка скрипта без
обновления хэша в `manifest.csv` — ошибка валидации. Это исключает дрейф
между документацией и кодом.

## 5. Скрипты

- Каждая задача автоматизации реализуется **двумя** файлами: `.ps1` (Windows) и `.sh` (Linux).
  Единственное исключение — `disk-image.sh`: `ocs-sr` существует только в Clonezilla Live.
- Имя одинаковое, отличается только расширение: `check-flash.ps1` / `check-flash.sh`.
- Обязательны: поддержка dry-run (`-WhatIf` / `--dry-run`), лог в файл,
  ненулевой код возврата при ошибке.
- **Лог в файл.** Путь не задаётся ключом, он фиксирован: каталог временных
  файлов плюс имя скрипта.
  - `.sh`: сразу после строки `set` — самоперезапуск через `tee`, где
    `LOG_FILE="${TMPDIR:-/tmp}/${0##*/}.log"`:

    ```bash
    if [ -z "${_LOGGED_SELF:-}" ]; then
        _LOGGED_SELF=1 exec bash "$0" "$@" 2>&1 | tee -a "$LOG_FILE"
        exit "${PIPESTATUS[0]}"
    fi
    ```

    Именно самоперезапуск, а не `exec > >(tee -a ...)`. Раньше применялся
    process substitution с `trap 'exec >&- 2>&-; wait' EXIT`, и это работало,
    пока скрипт доходил до конца. Если же `set -e` обрывает его внутри
    функции, `wait` в `trap` ждёт `tee`, который ещё жив, и скрипт виснет:
    вместо кода возврата вызывающий получает 124 по таймауту. Проверено
    прогоном 2026-10-14 на `tools/scripts/system-audit.sh`.
    Код возврата возвращается через `PIPESTATUS`, поэтому для вызывающего
    поведение не меняется, а лог дописывается до конца: `tee` стоит в
    конвейере, и оболочка ждёт его завершения.
  - `.ps1`: `Start-Transcript -Append` в `%TEMP%\<имя>.log` плюс
    `Register-EngineEvent -SourceIdentifier PowerShell.Exiting`, иначе
    транскрипт не закрывается при `exit` внутри скрипта.
  - `.ps1`: `Set-StrictMode -Version Latest` в начале скрипта, сразу после
    `param()`. Без него обращение к необъявленной переменной молча даёт
    `$null` вместо ошибки: опечатка в имени параметра превращается в тихое
    неверное поведение. Проверено на своём коде — параметр использовался, но
    не был объявлен в `param()`, и это не обнаруживалось до проверки.
  - `.ps1`: для внешних программ успех определяется по `$LASTEXITCODE`, а не
    по `$?`. Cmdlet'ы бросают non-terminating ошибки, поэтому нужна
    `-ErrorAction Stop` или `$ErrorActionPreference = 'Stop'`.
- Деструктивные действия (форматирование, удаление, запись на диск) — только
  после явного флага `--yes` / `-Force` и вывода предупреждения.
- `.sh`: `#!/usr/bin/env bash` + `set -euo pipefail`.
  Исключение — `scripts/repo-validate.sh`: он копит счётчики проверок и
  обязан доходить до итогового вывода, поэтому `-e` не включён, а обоснование
  записано комментарием в самом файле. Проверено прогоном: с `-e` выполнение
  обрывалось на разделе `[5/6]`.
- `.ps1`: `#Requires -Version 5.1` + `[CmdletBinding()]` + `$ErrorActionPreference = 'Stop'`.
- Правка любого скрипта из `manifest.csv` (`type=module|script`) меняет его
  SELF-HASH: строку манифеста нужно пересчитать, иначе `scripts/csv-check.py`
  вернёт код 1. Алгоритм — конкатенация отсортированных файлов сущности,
  в манифест пишется полный SHA256 (64 символа), не сокращение.

Правила раздела контролирует `tests/test_rules.py`; правило дуальности и
свежесть SELF-HASH — тоже.

## 6. Станционные сборки

Каталог `ventoy-partition/builds/<Станция>/` описывает работы по одной
конкретной машине. Имя каталога: `<Вендор>_<Модель>_<ОС>_<Версия>`,
например `MSI_B12M-211RU_Win11_LTSC_IoT_24H2`.

### Правило algorithm.md (обязательное)

> **Для каждого билда каждой станции обязателен файл `algorithm.md`** —
> он описывает весь цикл от живой ОС до валидации развернутой системы,
> включая статусы сети для каждого шага (критично для защиты от телеметрии
> до её блокировки), плюс инструкции и рекомендации по дальнейшей
> эксплуатации.

Шаблон: `ventoy-partition/builds/_templates/algorithm.md`.

Минимальный состав, который проверяет `scripts/repo-validate`:

| Требование | Как проверяется |
|------------|-----------------|
| Файл существует в каталоге каждой станции | обход подкаталогов `builds/` |
| Есть раздел «Порядок шагов» | заголовок уровня `##` |
| Есть раздел «Валидация развёрнутой системы» | заголовок уровня `##` |
| Есть раздел «Рекомендации по дальнейшей эксплуатации» | заголовок уровня `##` |
| Есть раздел «Не проверено на месте» | заголовок уровня `##` |
| Таблица шагов содержит колонку «Сеть» | разбор строк таблицы внутри раздела |
| В таблице шагов есть значения статуса сети | `online` / `offline` в строках таблицы |

Разделы ищутся именно как заголовки уровня `##`. Подзаголовок шага (`### Шаг 13.
Валидация развёрнутой системы`) или упоминание фразы в строке таблицы разделом
не считаются — иначе проверка вырождается в поиск слова по документу.

Отсутствие `algorithm.md` — ошибка валидации, коммит блокируется.

Каталог `_templates/` станцией не считается и правилу не подчиняется.

### Правило файла ответа (обязательное)

> **Для каждой задачи и каждой сборки — свой файл ответа.** Шаблон
> `autounattend.xml` лежит **в каталоге сборки** (`answer/`), а не в общем
> каталоге `ventoy/autoinstall/`. В `algorithm.md` сборки обязаны быть точные
> указания: **куда положить** файл на флешке и **какие строки и секции
> `ventoy.json` вставить, отредактировать или удалить перед установкой**.

**Обоснование.** Каждая сборка уникальна: она обязана учитывать характеристики
станции (объём и тип накопителя, объём памяти, наличие TPM), конкретный образ
(редакция внутри `install.wim`, версия установщика) и конкретное техническое
задание, собранное из требований конечного пользователя. Общий шаблон на все
станции не может учесть ни одного из трёх: жёстко заданный размер раздела
окажется неверным для другого накопителя, выбор редакции — для другого образа,
а состав пропускаемых экранов OOBE — для другого заказчика.

**Что из этого следует:**

| Следствие | Почему |
|-----------|--------|
| Каталог `ventoy/autoinstall/` не хранит файлы ответов | Он описывает механику плагина; общий файл там применялся бы к чужим станциям |
| Файл ответа **нельзя** класть в корень флешки | Дефект Ventoy 1.1.05: файл в корне применяется ко всем ISO, отказаться нельзя (`research/16`, N3) |
| Блок `auto_install` в `ventoy.json` правится перед установкой | Привязка ведёт на файл в каталоге сборки; сам файл копируется на флешку по инструкции из `algorithm.md` |
| Диск в файле ответа — только переменной `$$VT_…$$` | Жёсткий `DiskID 0` может поставить ОС на флешку (`research/16`, N2) |
| Файл обязан содержать проход `windowsPE` | Без него Setup не кэширует файл и молча уходит в ручной режим (`research/16`, N1) |

## 7. Исследования и сторонние решения

Правило введено на Этапе 4.3 и распространяется на все последующие этапы.
Оба подпункта обязательны; пропуск любого из них считается нарушением
регламента и блокирует сдачу этапа.

### 7.1. Обязательная последовательность до собственной реализации

Перед тем как писать собственный скрипт, сценарий или набор правок:

1. **Сформулировать цель.** Чего именно нужно добиться, каким результатом это
   измеряется. Цель записывается в план этапа, а не держится в голове.
2. **Провести масштабное актуальное исследование** в контексте цели: что уже
   существует, какие механизмы применяются, что задокументировано
   производителем, что проверено сообществом. Результаты фиксируются в
   `research/` с датой и указанием источников.
3. **Проанализировать и систематизировать** найденное: разделить на
   применимое и неприменимое к нашему профилю (коммерческое использование,
   зоопарк железа, выезд без вскрытия станций, LTSC 2024).
4. **Выделить паттерны** — конкретные механизмы, сущности и приёмы, которые
   стоит внедрить. Паттерн без указания, где именно он применяется, паттерном
   не считается.

Своя реализация оправдана только после того, как пройден весь список. Если
готовое решение закрывает цель — пишется своя обвязка вокруг него, а не
дубликат.

### 7.2. Обязательный запрос на использование сторонней утилиты

Если в результате исследования выяснилось, что сторонняя утилита или связка
утилит покрывает задачу, а собственная реализация была бы:

- **избыточна** — переписывание готового без выигрыша,
- **неэффективна** — готовое делает больше или надёжнее,
- **невозможна** — требует данных, прав или механизмов, которых у нас нет,

— использование готового решения **предлагается пользователю и согласуется с
ним до начала реализации**. Согласование включает: рекомендации, их
обоснование, альтернативы и то, чего сделать не удастся. Решение принимает
пользователь; без его ответа реализация не начинается.

Действует вместе с правилом комплектования TOOLS: сначала проверяется наличие
в Strelec, затем альтернатива из Strelec, затем портативный бесплатный аналог.

### 7.3. Что фиксируется по итогу исследования

| Поле | Требование |
|------|-----------|
| Дата | Обязательна — утилиты и ключи реестра устаревают |
| Источники | Ссылки на первоисточник, не на пересказ |
| Версии | Точные; если источники расходятся — пометка о расхождении |
| Лицензии | Проверены на предмет коммерческого использования |
| «Не проверено» | Явный раздел с непроверенными утверждениями |

Исследования складываются в `research/` и индексируются в
`research/01-research-index.md`.

## 8. Регламент git

1. Работа ведётся в ветке `arena/6bb077ac-immutable-workstation2`.
2. Один этап плана = один коммит. Сообщение: `Этап N: <суть>`.
3. Перед коммитом обязательно прогнать `repo-validate` — он не должен возвращать ошибок.
4. После каждого этапа — уведомление пользователю: что сделано, что проверено,
   какой коммит предложен.
5. Пустые каталоги удерживаются файлом `.keep`.

## 9. Чего в репозитории быть не должно

- Паролей, ключей, токенов, приватных ключей, сертификатов.
- Дампов с реальными данными клиентов и образов чужих машин.
- Лицензионных ключей активации в открытом виде.
- Бинарников и архивов (только заглушки).

## 10. Навигация по сущностям

Правило введено 2026-10-15 по решению заказчика. Основание и разбор —
`research/20-navigation-paths.md`.

**Проблема.** Один документ описывает сущности, которые лежат на двух разных
разделах флешки и в репозитории. Без объявленной системы отсчёта путь
`drivers/` означает каталог сборки, а `tools/backup/` — корень репозитория,
и отличить одно от другого по записи нельзя. На 724 строки `algorithm.md`
приходилось 10 ссылок, а 11 сущностей были названы без пути: мастер искал
скрипт перебором каталогов.

### 10.1. Префикс базы пути

Каждый путь к сущности начинается префиксом. Префикс объявляет, откуда путь
считается.

| Префикс | Откуда считается | Раскрытие в репозитории |
|---|---|---|
| `VENTOY:/` | корень раздела Ventoy, exFAT | `ventoy-partition/` |
| `TOOLS:/` | корень раздела Tools, NTFS | `tools/` |
| `BUILD:/` | каталог текущей сборки | `ventoy-partition/builds/<станция>/` |
| `REPO:/` | корень репозитория | как есть |
| `SYSTEM:` | команда или путь ОС, не сущность флешки | не раскрывается и не проверяется |

Запрещены: путь без префикса, если база пути не объявлена; многоточие внутри
пути (`builds/.../drivers`); префикс без продолжения.

**Объявление базы вместо префикса у каждого пути.** Документ, который описывает
репозиторий, а не флешку, вправе не ставить префикс у каждого пути: достаточно
объявить базу один раз. Объявление — строка в начале документа:

```
> **База пути.** Непомеченные пути в этом документе считаются от корня
> репозитория. Префиксы раздела 10.1 применяются там, где путь указывает
> на раздел флешки.
```

| Документ | База | Префиксы обязательны |
|---|---|---|
| `algorithm.md` сборки и его шаблон | объявляется картой сущностей | **да**, у каждого пути |
| `PLAN.md`, `README.md`, `tools/docs/`, `README.md` каталогов | объявляется строкой «База пути» | только для путей на раздел флешки |
| `research/` | исследовательские записи | нет |

Обоснование: неоднозначность возникает там, где один текст описывает два
раздела флешки одновременно. В документе о репозитории путь от корня однозначен,
и префикс у каждой из сотен записей добавил бы шума, не добавив смысла.
Проверяется и то и другое: наличие объявления и разрешимость пути по
объявленной базе.

Примеры раскрытия:

| Запись | Файл на диске |
|---|---|
| `VENTOY:/ISO/winpe/WinPE_11-10_Sergei_Strelec_x86_x64_RU.iso` | `ventoy-partition/ISO/winpe/…iso` |
| `TOOLS:/scripts/apply-blocking.ps1` | `tools/scripts/apply-blocking.ps1` |
| `BUILD:/answer/autounattend-ltsc-2024.xml` | `ventoy-partition/builds/<станция>/answer/…xml` |
| `REPO:/research/07-blocking-mechanisms.md` | `research/07-blocking-mechanisms.md` |
| `SYSTEM:C:\Windows\Panther\unattend.xml` | не проверяется |

### 10.2. Ссылка на первое упоминание

Первое упоминание нашей сущности в документе — markdown-ссылка на её файл
в репозитории:

```
[`apply-blocking.ps1`](tools/scripts/apply-blocking.ps1)
```

| Что | Правило |
|---|---|
| Наши сущности | скрипты, процедуры, конфигурации, файлы ответа, образы, утилиты, модули — ссылка обязательна |
| Средства ОС | `diskpart`, `DISM`, `pnputil`, `slmgr`, `powercfg` — не сущности репозитория, помечаются `SYSTEM:` |
| Внутри блока кода | markdown-ссылка невозможна; путь даётся комментарием в том же блоке |
| Повторное упоминание | ссылкой не оформляется, если сущность уже связана выше по документу |

Ссылка ведёт на файл репозитория — это единственный адрес, который можно
проверить. Путь на флешке даётся рядом префиксом из 10.1: `tools/` и `builds/`
лежат на разных разделах.

### 10.3. Раздел «Средства» в каждом шаге

Каждый шаг `algorithm.md` содержит раздел «Средства» — **всегда**, в том числе
когда шаг выполняется только средствами ОС. Раздел ставится между «Сеть» и
«Действия».

```
**Средства.**

| Сущность | Тип | Путь на флешке |
|---|---|---|
| `export-drivers.ps1` — markdown-ссылкой на файл | скрипт | `TOOLS:/backup/initial_backup/scripts/export-drivers.ps1` |
| `diskpart` | средство ОС | `SYSTEM:` |
```

Шаг без наших сущностей перечисляет средства ОС. Это не формальность: по
колонке «Путь на флешке» мастер открывает файл на носителе, не открывая
репозиторий, а по строкам `SYSTEM:` видно, что ничего скачивать не нужно.

### 10.4. Карта сущностей

`algorithm.md` содержит раздел «Карта сущностей» — одну таблицу со всеми
сущностями алгоритма: тип, раздел флешки, путь на флешке, номера шагов.
За таблицей — пояснение баз пути. Это единственный экран, по которому
собирается чемодан на выезд.

### 10.5. Что проверяется автоматически

| Параметр | Где | Как считается |
|---|---|---|
| Число разделов «Средства» равно числу шагов | `repo-validate`, `test_navigation.py` | `### Шаг N` против `**Средства.**` |
| У каждой нашей сущности в шаге есть рабочая ссылка | `test_navigation.py` | имена файлов в тексте шага против ссылок шага |
| Раздел «Карта сущностей» есть | `repo-validate` | заголовок в `algorithm.md` |
| Каждый путь с префиксом разрешим | `test_navigation.py` | раскрытие по таблице 10.1 и `os.path.exists` |
| Многоточий в путях нет | `test_navigation.py` | поиск `...` и `…` в путях |
| Префикс не употреблён без продолжения | `test_navigation.py` | `TOOLS:/` без имени файла — ошибка |
| Все относительные ссылки живы | `test_repo.py` [6] | обход всех `.md`, `os.path.exists` |
| Шаблон соответствует правилу | `test_navigation.py` | `_templates/algorithm.md` проверяется тем же набором |

Внешняя утилита проверки ссылок не добавляется по решению заказчика:
`test_repo.py` [6] проверяет все относительные ссылки без зависимостей,
а lychee и markdown-link-check не умеют ни перечень средств, ни префиксы.

## 11. Протокол исполнения

Раздел внесён 2026-10-15. До этого протокол применялся, но нигде не был
записан: он жил в рабочей переписке и терялся при её сжатии между сегментами.
Отсутствие записи — дефект по определению раздела 12: утверждение «регламент
исполнения зафиксирован в репозитории» было ложным.

### 11.1. Три фазы задания

| Фаза | Что делается | Результат |
|---|---|---|
| **AUDIT** | фактическое состояние против требуемого; исследования; находки с метками | документ `research/NN-<тема>.md` с нумерованными находками |
| **CONSTRUCT** | закрытие находок; код, документация, проверки | правки и проверки, которые их ловят |
| **CHRONICLE** | фиксация: план, журнал, сводка, коммит | запись в `PLAN.md`, `CHANGELOG-flash.md`, `git` |

Не более трёх итераций на задание. Если за три итерации находка не закрыта,
она выносится пользователю как открытая, а не правится четвёртый раз.

Находки AUDIT нумеруются в пределах документа и на них ссылаются проверки.
Сквозная нумерация классов дефектов — в пуле раздела 12, это разные сущности:
находка это экземпляр, класс это тип.

### 11.2. Обязательный запрос при сомнении

При сомнении или конфликте задаётся вопрос. Домысливание запрещено:
предположение, выданное за факт, в этом проекте уже приводило к дефектам —
см. класс B-04 пула.

Запрос обязан содержать:

| Что | Зачем |
|---|---|
| Утверждение или находку | чтобы вопрос был о конкретном, а не о настроении |
| Источники, которые уже проверены, и что в каждом найдено | чтобы не просить того, что можно прочитать |
| Два варианта и последствия каждого | чтобы решение принималось между альтернативами |
| Один вопрос | каскад вопросов дороже самой работы |

### 11.3. Приоритет источников

Когда два источника утверждают разное, выше тот, что раньше в списке:

| № | Источник | Почему здесь |
|---|---|---|
| 1 | Решение заказчика | воля владельца задачи |
| 2 | Факт носителя или железа | не оспаривается и не редактируется |
| 3 | Внешний источник | документация вендора, лицензия, версия |
| 4 | `CONVENTIONS.md` | правило проекта |
| 5 | `PLAN.md` | план может устареть против решения |

Запрос по конфликту источников нужен только если спорят источники одного
уровня. На практике это редкость, и почти любое расхождение разрешается
этой таблицей без вопроса.

### 11.4. Когда запрос обязателен

| Триггер | Условие | Как проверяется |
|---|---|---|
| **Т1** | Утверждение не сводится ни к одному из пяти источников раздела 12.1 | попыткой назвать файл и строку |
| **Т2** | Два источника одного уровня утверждают разное | наличием двух цитат |

Оба триггера проверяемы. «Похоже на», «вероятно» и «обычно так делают»
триггером не являются: это признаки того, что источник не найден, то есть Т1.

### 11.5. Сверка перед push

Перед `git push` обязательно: `git fetch` и сравнение `HEAD` с
`origin/<ветка>`. Окружение может пересобрать клон между ходами, и тогда
локальная история короче удалённой — push поверх неё теряет работу.
Наблюдалось трижды, см. класс B-08 пула.

При рассинхроне: `git reset <remote-HEAD>` (индекс и HEAD к удалённой ветке,
рабочее дерево не трогается), затем пересобрать коммит из фактических
изменений. `git reset --soft` для этого не годится: он оставляет индекс от
прежнего HEAD, и все файлы выглядят удалёнными.

## 12. Определение дефекта и пул дефектов

Раздел появился из 36 задокументированных находок AUDIT. Ни одна не была
учтена как дефект с порогом и проверкой, потому что самого понятия дефекта
в репозитории не было. Без определения каждый разбор заново решал, что
считать ошибкой, и четыре раза одно и то же решение принималось иначе.

### 12.1. Что такое дефект

**Дефект существует, когда одновременно:**

- **А.** Есть опровержимое утверждение о состоянии репозитория: «X есть»,
  «X равен N», «X лежит там-то», «X делает то-то».
- **Б.** Утверждение ложно против одного из пяти источников обязательства,
  и **источник называется явно, с файлом и строкой**:

| Источник | Пример |
|---|---|
| Решение заказчика | «persistence 16 ГБ», «GTweak не входит» |
| Факт носителя или железа | GPT, `VTOYEFI` 32 МБ, i3-1215U, exFAT |
| Внешний источник | документация вендора, страница выпуска |
| `CONVENTIONS.md` | любое правило этого файла |
| `PLAN.md` | план работы |

Следствие: исправление дефекта меняет **либо** состояние репозитория,
**либо** источник обязательства. Поэтому у каждой записи пула обязательно
поле `fix_target`: `state` — правим репозиторий; `doc` — правим документацию
или правило; `decision` — нужен запрос к заказчику.

### 12.2. Что дефектом не является

Восемь случаев, которые раньше попадали в разбор как «проблемы». Ни один не
подходит под 12.1 — в каждом отсутствует опровержимое утверждение о
расхождении с источником:

1. **Приём или паттерн**, принятый к использованию. Опровергать нечего.
2. **Реестр или каталог средств** (реестр драйверов, список утилит). Это
   справочник, а не утверждение о состоянии.
3. **Ограничение среды исполнения** (нет PowerShell в среде проверки, нет
   NuGet). Среда не является источником обязательства о репозитории.
4. **Факт железа** (8 ГБ распаяно, TPM отсутствует). Факт не бывает ложным.
5. **Решение заказчика не делать** (роутеры исключены, синхронизация не
   нужна). Отсутствие сделано сознательно и зафиксировано.
6. **Осознанное «не проверено»** с записанной причиной. Это состояние
   знания, а не расхождение.
7. **Внешнее событие** (вышел новый выпуск, закрыт сайт вендора). Реестр не
   обязан предвидеть будущее; устаревание — повод обновить, не дефект.
8. **Оформление без фактического противоречия** (порядок разделов, стиль).
   Становится дефектом только если порядок закреплён правилом.

### 12.3. Протокол классификации

Четыре шага, выполняются по порядку, без циклов:

1. **Свести к утверждению.** Сформулировать находку как опровержимое
   утверждение. Не сводится → дефекта нет, условие А не выполнено.
2. **Назвать источник.** Файл и строка. Не удаётся назвать → **Т1, запрос**
   (см. 11.4). Угадывать источник нельзя.
3. **Сверить.** Совпадает → дефекта нет. Расходится → дефект. Два источника
   одного уровня спорят → **Т2, запрос**.
4. **Записать.** Класс, основание, `fix_target`, `source`. Запись идёт в
   `research/bestiary.csv`.

Новый класс заводится только после того, как определения 12.1 и 12.2
применены к не менее чем трём реальным случаям. Один случай классом не
становится — иначе пул превращается в список всех находок.

### 12.4. Форма запроса к заказчику

Запрос по триггеру Т1 или Т2 содержит четыре части и ничего больше:

1. Утверждение, которое не удаётся проверить.
2. Проверенные источники и что в каждом найдено.
3. Два варианта действий с последствиями каждого.
4. **Один вопрос.**

Запрос без варианта действий не принимается: он перекладывает анализ на
заказчика. Запрос с тремя и более вопросами не принимается: он не решает ни
одного до конца.

### 12.5. Пул дефектов

`research/bestiary.csv` — реестр повторяющихся дефектов. Колонки:

| Колонка | Значение |
|---|---|
| `id` | `B-NN`, не переиспользуется |
| `signature` | Признак класса: что именно повторяется |
| `n` | Сколько раз встречался |
| `first_seen` | Дата первой встречи, обязательна и для разовых |
| `last_seen` | Дата последней встречи |
| `fix_target` | `state`, `doc` или `decision` |
| `closes` | Какая проверка закрывает класс; пустое, если проверки нет |
| `verdict` | `automated`, `open`, `wontfix` |
| `source` | Где класс задокументирован |

Разовые находки тоже попадают в пул, с `n = 1` и датами: дата нужна, чтобы
повтор через полгода был виден как повтор, а не как новая находка.

### 12.6. Порог автоматизации

Класс с **`n >= 2`** обязан получить проверку в `tests/` и значение
`verdict = automated`. Проверка входит в `tests/run-all.py`.

Класс с `n = 1` остаётся `open` и проверки не требует. Это сознательный
отказ от автоматизации единичного: проверка ради одного случая дороже
повторного ручного разбора. У такой записи `closes` пустое, и проверка пула
это допускает: требование проверки привязано к порогу, а не к факту записи.

Мета-класс «найденный дефект не учтён в пуле» имеет отдельный порог: сам
факт находки вне пула — уже второй случай, если первый был записан. Отсюда
правило: **дефект, найденный в AUDIT, записывается в пул в том же коммите**.

### 12.7. Проверка пула

`tests/test_bestiary.py` проверяет сам пул, а не только продукт:

- каждая запись имеет полный набор колонок и валидные значения;
- `n >= 2` влечёт непустое `closes` и `verdict = automated`;
- проверка из `closes` существует и зарегистрирована в `run-all.py`;
- `n >= 1` влечёт обе даты заполненными;
- `id` уникальны.

### 12.8. Закрытие записи

Класс закрывается только возвратом дефекта: состояние, которое ловит
проверка, воспроизводится в копии репозитория, прогон падает, копия
удаляется. Прогон на неповреждённом репозитории доказывает лишь то, что
проверка не мешает, — закрытием это не является.

Возврат бывает двух видов, и оба законны:

- **возврат состояния** — правка продукта: строка манифеста, битая ссылка,
  испорченный заголовок раздела. Так закрываются классы с `fix_target = state`;
- **возврат правила** — удаление или порча текста правила, которое проверяет
  тест. Так закрываются классы с `fix_target = doc`: их проверка читает
  правило, и возврат для неё — отсутствие правила.

Проверено 2026-10-15 на копиях: 10 возвратов, каждый роняет названную в
`closes` проверку. Протокол прогона возврата — в `research/README.md`.

Класс, чей возврат не определён, обязан иметь в `source` пометку
«возврат не определён» и причину. Молчаливое отсутствие возврата делает
запись неотличимой от закрытой.

`verdict = wontfix` ставится только решением заказчика и только с записью
этого решения в поле `source`. Молчаливое прекращение работы над классом
закрытием не является.

### 12.9. Правило одного источника ожидаемого значения

Побочный продукт классификации: класс B-01 «факт репозитория зашит в тест
константой» повторялся 11 раз. Его лечение — не внимательность, а правило:

**Ожидаемое значение, которое выводится из репозитория, хранится в
`tests/baseline.csv` в одном экземпляре. Тест читает его через
`expected()` из `tests/baseline.py`.**

Добавление сущности в манифест правит одну строку `baseline.csv`, а не
одиннадцать тестов. Проверено возвратом дефекта на копии: сущность плюс
правка одного файла дают ноль падений из 16 тестов.

Что в `baseline.csv` **не кладётся**:

- **инварианты** — «образов должно быть семь», «подкатегорий не меньше N».
  Их падение и есть сигнал; вынести инвариант отсюда значит ослабить
  проверку до сверки файла с самим собой;
- **границы** — `> 30`, `>= 1`. Это требование, а не копия факта;
- **значения, которые тест вычисляет сам** и сравнивает между собой.

Граница между копией и инвариантом: копия описывает то, что есть и может
законно измениться; инвариант описывает то, что нарушать нельзя.

**Разделы 11 и 12 проверяет `tests/test_rules.py`. Пул проверяет
`tests/test_bestiary.py`.**
