# Резервное копирование разделов флешки

Решения владельца от 2026-10-15:

| Вопрос | Решение |
|--------|---------|
| Куда | **Внешний диск**, хранится отдельно от флешки |
| Объём | **Конфиг и `builds/`** — не полные образы разделов |
| Периодичность | **Раз в месяц**, плюс после любого изменения конфига |

## Почему не полный образ разделов

Раздел 0 — 340.72 ГБ, раздел 2 — 128 ГБ. Полный образ — это часы на снятие и
сотни гигабайт на хранение. При этом **образы и утилиты восстанавливаются
скачиванием по `manifest.csv`**: там указаны источник, SHA256, размер и версия
каждого файла. Копировать их — значит копировать то, что уже описано и может
быть получено заново.

Невосстановимое скачиванием — другое:

- `ventoy/ventoy.json` — конфиг, проверенный на этой флешке;
- `ventoy/persistence/` — файл persistence 16 ГБ с накопленными изменениями;
- `builds/` — станционные сборки, файлы ответов, драйверы конкретной станции;
- дампы первых секторов — без них восстановление разметки вслепую;
- `reports/` — отчёты о работах.

Всё это маленькое по объёму и дорогое по содержанию.

## Что копировать

| Что | Откуда | Почему не восстанавливается иначе |
|-----|--------|----------------------------------|
| `ventoy/ventoy.json` | раздел 0 | Конфиг под эту флешку |
| `ventoy/persistence/` | раздел 0 | Накопленные изменения Live-системы |
| `ventoy/autoinstall/`, `script/`, `theme/` | раздел 0 | Наши файлы, не из поставки |
| `builds/` | раздел 0 | Станционные сборки |
| `backup/` | раздел 0 | Дампы первых секторов |
| `docs/` | раздел 2 | Есть в git, но копия не помешает |
| `manifest.csv`, `CONVENTIONS.md`, `PLAN.md` | репозиторий | Есть в git |

**Отдельно про persistence.** Файл `persistence/linuxmint-22.3-cinnamon_casper-rw_16GB.dat`
— 16 ГБ. Это единственный крупный объект в списке. Копировать его имеет смысл
только если в Live-системе накоплено что-то ценное; после чистой настройки
копия не нужна. Решение принимать по факту, и записывать его в журнал.

## Дампы первых секторов

Снимаются **до любых правок разметки**. Хранятся в `backup/` на разделе 0 и в
копии на внешнем диске.

```bash
# Определить устройство, убедиться, что это именно флешка
lsblk -o NAME,SIZE,MODEL,SERIAL

# Первые 34 сектора: MBR + полная GPT (34 × 512 = 17408 байт)
dd if=/dev/sdX of=backup/gpt-first34-$(date +%Y%m%d).img bs=512 count=34

# Резервная GPT в конце диска — последние 34 сектора
SIZE=$(blockdev --getsz /dev/sdX)
dd if=/dev/sdX of=backup/gpt-backup34-$(date +%Y%m%d).img bs=512 \
   skip=$((SIZE - 34)) count=34
```

В Windows то же делает `diskpart` или `dd` из состава Strelec.

**Проверка дампа обязательна:** размер файла 17408 байт, и он не пустой.

```bash
ls -l backup/*.img
```

### Восстановление разметки из дампа

Операция разрушительная и выполняется только когда разметка уже повреждена.

```bash
dd if=backup/gpt-first34-20261015.img of=/dev/sdX bs=512 count=34
```

После восстановления — перечитать таблицу разделов и убедиться, что разделы
видны. Содержимое разделов дамп не возвращает, только таблицу.

## Куда и как складывать

Внешний диск, каталог с датой:

```
<внешний диск>/flash-backup/
  2026-10-15/
    ventoy.json
    persistence/          (если копируется)
    builds/
    backup/               (дампы секторов)
    manifest.csv
    check-flash.log       (вывод сверки на дату бэкапа)
  2026-11-15/
    ...
```

Правила:

- **Диск хранится не вместе с флешкой.** Бэкап на том же носителе, который
  вышел из строя, — не бэкап.
- Каталог с датой не перезаписывается, новый бэкап кладётся рядом.
- Старые каталоги удаляются осознанно, не автоматически.
- **Клиентские данные сюда не кладутся никогда.** Это бэкап флешки, не
  бэкап станций.

## Порядок ежемесячной проверки

1. Подключить флешку и внешний диск.
2. Снять дамп секторов, если правки разметки были или дамп старше трёх месяцев.
3. Скопировать список из таблицы выше в каталог с текущей датой.
4. Запустить сверку и сохранить вывод:

   ```bash
   bash scripts/check-flash.sh --ventoy <раздел0> --tools <раздел2> --verify \
        | tee <внешний диск>/flash-backup/$(date +%Y-%m-%d)/check-flash.log
   ```

5. Посмотреть итог сверки. **Код 0 при нуле сверенных сумм — не
   благополучие**, а отсутствие файлов для сверки.
6. Внести запись в [`CHANGELOG-flash.md`](CHANGELOG-flash.md): дата, что
   скопировано, итог сверки, что не проверено.

## Восстановление флешки из бэкапа

| Что случилось | Что делать |
|---------------|-----------|
| Повреждён `ventoy.json` | Скопировать из бэкапа, проверить `check-flash` |
| Удалён или испорчен файл ответа | Взять из `builds/` в бэкапе или из git |
| Слетел persistence | Восстановить файл из бэкапа, либо создать заново (`CreatePersistentImg.sh -s 16384 -t ext4 -l casper-rw`) |
| Повреждена таблица разделов | `dd` из дампа, см. выше |
| Раздел 0 стёрт | Переустановка Ventoy (`reinstall.md`), затем восстановление конфига и `builds/` из бэкапа |
| Утерян образ или утилита | Скачать заново по `manifest.csv`, сверить SHA256 |

## Не проверено

- Дамп секторов на этой флешке **не снят**: каталог `backup/` пуст, только
  `.keep`. Команды приведены, но не выполнялись.
- Совместимость `dd` из состава Strelec с exFAT-разделом 340 ГБ не проверялась.
- Время копирования persistence 16 ГБ на внешний диск не измерялось.
- Восстановление разметки из дампа не выполнялось ни разу.
- Ёмкость внешнего диска и фактический размер бэкапа не известны.
