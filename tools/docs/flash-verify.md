# Сверка содержимого флешки с manifest.csv

Один проход, который сверяет всё, что сверить можно, и порядок действий, если
что-то не сошлось.

Документ закрывает задачу A3 из
[`../../research/24-next-steps.md`](../../research/24-next-steps.md).

> **База пути.** Непомеченные пути в этом документе считаются от корня
> репозитория. Префиксы `CONVENTIONS.md` §10.1 применяются там, где путь
> указывает на раздел флешки.

## Проход существует, он был и раньше

Задача A3 формулировалась так, будто не хватает «прохода, который сверяет все
строки с суммой за один запуск». Это неверно: проход есть, это
`check-flash --verify`, и он сверяет все типы сущностей за один вызов.
Формулировка задачи исправлена в `research/24`, §3.

Чего действительно не было — порядка действий при расхождении. Он ниже, в
разделе «Если сумма не сошлась».

## Что сверяется чем: покрытие по факту

`manifest.csv` — 46 строк. Строки с заполненной ожидаемой суммой — 28. Они
делятся на две непересекающиеся половины, и сверяются они разными командами:

| Что | Строк | Чем сверяется | Почему именно этим |
|-----|-------|---------------|--------------------|
| Образы и утилиты: поле `file` заполнено, сумма есть | **11** (1 `iso` + 10 `tool`) | `check-flash --verify` | Бинарники лежат на разделах флешки, в git их нет |
| Скрипты и модули: сумма есть, поле `file` пусто | **17** (11 `script` + 6 `module`) | `scripts/csv-check.py` | Это SELF-сущности: сумма считается по **набору** файлов, которые живут в git |
| Итого сверяемых | **28** | | |

Отдельно, и это **не** покрыто:

| Что | Строк | Состояние |
|-----|-------|-----------|
| `file` заполнено, сумма `PENDING` | **18** | Сверить нечем. `--verify` печатает «нет SHA256 — сверить нечем», это предупреждение, а не успех |
| Строки без суммы и без файла | 0 | — |

18 строк `PENDING` — это 6 образов и 12 утилит. Проход по ним физически
невозможен до появления ожидаемого значения; причина по каждой записана в
`manifest.csv` и в `research/23-license-scope.md`, N40.

### Почему две команды, а не одна

Свести всё в одну команду нельзя без нарушения `CONVENTIONS.md` §12.9 «один
источник ожидаемого значения». Сумма SELF-сущности считается по набору файлов
(`SELF_ENTITIES` в `scripts/csv-check.py`, от двух до девяти файлов на
сущность). Продублировать этот пересчёт в bash и PowerShell значило бы завести
второй и третий источник истины о том, как считается хеш, — и они разошлись бы
при первом изменении состава.

Поэтому: бинарники сверяет `check-flash`, SELF-сущности — `csv-check.py`,
и каждый остаётся единственным источником для своей половины.

## Команды

### Половина 1: образы и утилиты на флешке

Windows:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\check-flash.ps1 `
    -Ventoy E: -Tools F: -Verify
```

Linux:

```bash
bash scripts/check-flash.sh --ventoy /mnt/ventoy --tools /mnt/tools --verify
```

Без `--verify` / `-Verify` проверка сумм пропускается целиком, и скрипт
печатает «проверка SHA256 пропущена». Без `-Tools` / `--tools` утилиты не
проверяются, и в итоге появляется строка «не проверено N (не задан --tools)».

Код возврата: `0` — расхождений нет, `1` — есть расхождения, `2` — флешка не
найдена.

### Половина 2: скрипты и модули

В репозитории:

```bash
python3 scripts/csv-check.py manifest.csv
```

`csv-check.py` берёт корень из текущего каталога (`os.getcwd()`), поэтому тот
же запуск из корня смонтированной флешки сверяет **копию на носителе**, а не
копию в git:

```bash
cd /mnt/tools && python3 /путь/к/repo/scripts/csv-check.py manifest.csv
```

Если Python на машине с флешкой недоступен, эта половина остаётся
непроверенной на носителе, и это надо записать в «Не проверено», а не считать
покрытым через репозиторий.

## Если сумма не сошлась

Расхождение имеет три причины, и действие зависит от того, какая из них.
Определять надо от дешёвого к дорогому.

### Шаг 1. Сравнить размер, это бесплатно

`size_bytes` уже лежит в `manifest.csv`, хешировать ничего не нужно.

- **Размер другой** — на флешке лежит другой файл, а не испорченная копия
  того же. Дальше смотреть версию.
- **Размер тот же, сумма другая** — побитовое расхождение: недокачанный или
  повреждённый файл, либо пересобранный релиз того же объёма.

### Шаг 2. Записать фактическую сумму ДО любых изменений

Это обязательный шаг, и он идёт раньше восстановления файла:

```powershell
Get-FileHash -LiteralPath <файл> -Algorithm SHA256
```
```bash
sha256sum <файл>
```

Как только файл перезаписан, свидетельство того, что именно было не так,
уничтожено. Сначала запись, потом действия.

### Шаг 3. Определить, какая сторона неверна

| Признак | Неверно | Действие |
|---------|---------|----------|
| Версия в имени файла не совпадает с полем `version` | манифест устарел | обновить `version`, `sha256`, `size_bytes`, `added` одной правкой |
| Версия совпадает, сумма совпадает с суммой из первоисточника по `url` | файл на флешке | перекачать файл, сверить повторно |
| Версия совпадает, а первоисточник даёт ту же сумму, что на флешке | манифест | значение в манифесте было неверным с самого начала — править манифест по первоисточнику |
| Первоисточник недоступен | не определено | **не править ничего**, записать в «Не проверено» |

### Чего делать нельзя

> **Не править `manifest.csv` под файл на флешке, пока не установлено, какая
> сторона верна.** Это самый короткий путь к тому, чтобы неверное значение
> стало постоянным и перестало выглядеть неверным. Именно так устроен класс
> дефектов B-13: факт в двух местах, обновлено одно.

> **Не перекачивать файл до записи фактической суммы.** См. шаг 2.

> **Не считать предупреждение успехом.** «Отсутствует на флешке» и «нет
> SHA256 — сверить нечем» печатаются как предупреждения, и код возврата при
> них может остаться нулевым. Проход, в котором «сверено 0», — это не
> прошедшая проверка; скрипт сам печатает «ни одна контрольная сумма не была
> сверена с реальным файлом».

### Шаг 4. Записать как находку

Любое расхождение — находка по `CONVENTIONS.md` §12: что не сошлось, какая
сторона оказалась неверной, чем установлено. Разовые проблемы тоже идут в пул;
порог `n >= 2` нужен только для возврата дефекта как критерия закрытия.

## Что успешный проход НЕ означает

- **Не означает**, что 18 строк `PENDING` проверены. Их нечем проверять.
- **Не означает**, что файлы запускаются и работают. Сверка суммы подтверждает
  только то, что байты совпадают с ожидаемыми.
- **Не означает**, что SELF-сущности сверены на носителе, если `csv-check.py`
  запускался в репозитории, а не из корня флешки.
- **Не означает**, что ожидаемые суммы получены из первоисточника. У 10
  утилит суммы взяты из каталогов пакетных менеджеров при совпадении версии;
  как это получено — в `research/22` и `research/23`.
