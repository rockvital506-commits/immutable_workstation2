# События решений о точных ревизиях: формат и вычисление известного состояния

## Назначение и зависимости
ENT-0007 r0001 — protocol: decision-events.schema.json, events.py, verify.py,
usage.md. Точная зависимость: ENT-0004 r0002. Транзитивно выбираются ENT-0003
r0002 и ENT-0002 r0003, модель изменяемого дерева B. Само внедрение формата
не создаёт реального отзыва, ограничения, коррекции или снятия: для каждого
такого события нужно действительное явное решение владельца. Условное
разрешение разработки не выдаётся за волю отозвать существующую сущность.

## Типы и точные байты
Поддержаны approve_revision, restrict_use, revoke_use, lift_restriction и
correct_record для subject catalog_id/entity_id/revision и полного artifacts.
Общие поля наследуют определения утверждённой базовой схемы через фиксированный
URN, без копии второго описания. Схемы установлены локально, сверяются по
SHA-256, обе регистрируются в referencing.Registry; иной retrieval запрещён.
URI не разрешает сетевую загрузку. Старые approve_revision и registry не меняются.
События о release пока не поддержаны; subject не притворяется ревизией сущности.

Каждая запись неизменяема, имеет собственный UUID, дату, owner/recorded_by agent,
statement/quote либо summary и basis. reason обязателен для четырёх событий.
Текст/причина не исполняются и не являются языком условий. Имя записи:
catalog/approvals/<decision_id>.json, без временной метки. Ограничения не
скрываются в локальных отрицательных решениях о кандидатах.

## Область ограничения и снятия
scope содержит непустые уникальные operations и areas. Это точные строковые
идентификаторы; единственный wildcard — отдельное значение *. Иерархия имён,
префиксы, glob, regex и произвольные predicates не предполагаются. Значение
agent_system не означает автоматически agent_system.validation. Если владелец
имеет в виду все области/операции, это отражается явно через *. Неизвестный
дополнительный формат условия не игнорируется — запись отвергается.

Операция/область запроса должны быть конкретными, не *. Алгоритм вычисляет
действующие запреты только для этой пары и точных выбранных subjects.
Несколько restrict_use/revoke_use действуют совместно. lift_restriction
указывает decision_id и SHA-256 точной записи запрета, тот же subject/artifacts
и scope не шире исходного. Он снимает только указанный запрет и только свою
область. Частичное снятие export не снимает activate, а снятие одного запрета
не отменяет другой. lift на approval или другой lift не является допустимым
молчаливым изменением полномочий. Для нового запрета — отдельный restrict/revoke.

Даты и порядок файлов не задают приоритет. Новое approve_revision не отменяет
отзыв; новая ревизия не снимает запрет старой. Все ссылки на события проверяются
по ID/хэшу, subject/составу, отсутствию неполных или циклических цепочек.
Состояние не редактируется в исходной записи и не выбирается last-wins.

## Коррекция: поддержанная часть и остановка
correct_record указывает точную target-запись по UUID/хэшу, тот же subject и
полный artifacts, reason и непустые changes с path/old_value/new_value.
Проверяется исходное old_value и допустимость исправленного представления;
байты target не меняются. В этой версии автоматически обрабатываются ТОЛЬКО
/decision_date и /statement_form как документальные поля, не меняющие
структурированное разрешение. Новая дата должна быть календарно допустима.
Изменение statement_form описывает реальную коррекцию классификации источника,
не превращает отсутствующую цитату в существующую: её происхождение остаётся
предметом доверия и реального решения владельца, а не доказательством алгоритма.

Subject, artifacts, область/смысл разрешения, statement, basis и прочие поля
не исправляются автоматически: результат unsupported с требованием разрешить
семантическую коррекцию. Совпадающие документальные коррекции сохраняются;
разные new_value для одной пары target/field конфликтуют независимо от даты.
Повтор поля в одном событии — ошибка. Ссылки на исправляемый оригинал остаются
историческими; коррекция не меняет его digest и не снимает ограничений.

## API и граница результата
Вызов evaluate_decisions(decision_blobs, subjects, operation=..., area=...).
decision_blobs — dict относительный путь -> точные bytes ВСЕХ переданных
известных решений; subjects — непустой список точных идентичностей.
Сначала строгий JSON и Schema с date checker, UUID/пути, полные составы и
противоречия одобрений; затем ссылки/области/коррекции; затем scoped-запреты.
Состав каждого события должен совпадать с известным approve_revision того же
subject. Отсутствующее подтверждение не заменяется разрешением. Несвязанная
с индексом запись тоже разбирается; неизвестный тип/влияние не объявляется
безопасно посторонним. Лимиты: 10000 записей, 16 MiB на запись, 64 MiB всего.

Результат содержит schema_version=1, layer=known_entity_decisions, context с
точной парой operation/area и subjects, inputs с хэшами/размерами, active_blocks,
applied_lifts, corrections (ID/target/перечень полей, без новых значений),
diagnostics и not_checked. status: no_known_block_in_scope,
blocked_known_scope, failed или unsupported. Нет известных блокировок — НЕ
разрешение; во всех исходах overall_admission=not_evaluated и
transition_allowed=false. Диагностика — код без содержимого/частного пути.

Не проверяются получение/подлинность входов, связь с registry и реальные байты
артефактов/граф, глобальная полнота событий, release-события, семантические
коррекции, ядро, среда, активация. Эти обязанности не отменены. Успех не есть
атомарный снимок или знание будущих отзывов. Полноту caller доказывает отдельно;
результат не способен обнаружить непереданное событие. Отчёт локален, не
экспортируется автоматически. Нет записи/отката/активации/опасных действий.

## Проверка применения
В разрешённой среде из корня репозитория:
../.venv/immutable-agent-system/bin/python agent_system/specification/ent-0007/r0001/verify.py
37 тестов должны пройти без failures/errors/skips; сбой/прерывание не успех.
Фикстуры синтетические. Испытаны накопление/точечное снятие/частичные области,
перестановки/даты/новые одобрения, точные refs/составы, корректные и конфликтующие
коррекции, неизвестные типы/условия, парсер/движок/лимиты/отсутствие сети,
реальный положительный ledger без выдачи общего допуска. Происхождение решения
владельца и его смысл не доказываются наличием JSON-полей actor_role/basis.
