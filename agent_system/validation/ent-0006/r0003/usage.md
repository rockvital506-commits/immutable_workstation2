# Связывание известного состава, одобрений и графа

## Назначение, зависимости и граница
ENT-0006 r0003 — check. Нормативный состав: check.py, verify.py, usage.md.
Точные зависимости того же каталога: ENT-0004 r0002 (строгий JSON/Schema слой)
и ENT-0005 r0003 (проверяемое получение объявленных файлов в Linux-интеграции).
Транзитивно выбирается ENT-0002 r0003: модель изменяемого дерева B.
Дополнительная точная зависимость — ENT-0007 r0001 (схема/вычислитель событий).
Новые сторонние пакеты не нужны; используется ранее разрешённая среда/lock.

Это проверка целостности и согласованности явно предоставленных известных
входов, не полная процедура получения дерева или разрешение использования.
Самостоятельный источник одобрения — реальные решения владельца; совпадение
технических полей не доказывает их человеческое происхождение.

## Вызов и получение данных
check_catalog(registry_blob, witness_blobs, artifact_blobs, selection) принимает:
- точные bytes индекса;
- dict относительный путь -> bytes для всех решений предоставленного снимка;
- dict относительный путь -> bytes артефактов выбранного замыкания;
- непустой список точных catalog_id/entity_id/revision корней выбора.

Проверка не обходит исходную файловую систему, не достраивает snapshot по
одним положительным ссылкам и не делает сетевых запросов. Доверенная вызывающая
процедура отдельно получает и закрепляет точные входы, применяет безопасную
границу чтения, включает ВСЕ известные решения и обозначает предел полноты.
Непредоставленное событие этот слой не способен обнаружить; нельзя объявлять
историю полной только потому, что переданный набор прошёл проверку.
Ожидаемые хэши и доверенный корень индекса не должны выводиться из самих
непроверенных данных с последующим объявлением их одобренными.

Парсер и local_validator переиспользуются из точной установленной ENT-0004
r0002, не копируются. До загрузки проверяется её известный digest; код нельзя
выбрать входным registry или аргументом API. Схема ENT-0003 r0002 также проверяется
по точным байтам. Исполнение установленного проверенного инструмента не есть
исполнение содержимого входного каталога. Изменение зависимого кода требует
новой ревизии, не подстановки latest. Установленная среда инструментов доверенна;
защита от привилегированной подмены её кода вне области этого слоя.

## Проверяемые условия
Структура входов проверяется утверждённой схемой с календарным date checker.
Проверяются уникальность ENT/revision, ненулевые номера, полные составы и
отсутствие конфликтующих описаний одного физического пути. Одно и то же
согласованное описание файла может встречаться в нескольких версиях; разные
описания одного пути блокируются. Внутри версии пути уникальны независимо от role.

Каждое предоставленное решение разбирается по утверждённой базовой схеме
для approve_revision либо ENT-0007 для restrict/revoke/lift/correct. Проверяются
UUID/имя/subject/полный состав каждого события; индексное положительное
подтверждение обязано ссылаться именно на approve_revision, не на запрет.
Сырые links и полный набор артефактов совпадают. Независимый порядок файлов
состава не является порядком ссылочной цепочки.

Если есть события либо caller запросил scoped-проверку, operation и area
передаются явно. ENT-0007 вычисляет ограничения всего selected_closure, включая
обязательные зависимости, не только корни выбора. Без контекста результат
unsupported, а не отсутствие ограничений. Известный запрет даёт status
blocked_known_scope; для неограниченной выбранной пары возможно
passed_known_inputs, но общий допуск по-прежнему не выдан. Полный результат
событий вложен как restriction_evaluation с собственными границами; parent
убирает restriction_semantics из not_checked лишь после выполненной scoped-
проверки, оставляя глобальную полноту и семантические коррекции непокрытыми.

Неизвестный тип/условие, неполная ссылка или конфликт не игнорируется. Исторический
ENT-0006 r0001 остаётся неподдерживающим события и не переписывается.

Все точные отношения source-каталога должны разрешаться в известные записи
его namespace; федерация не угадывается. Это ограничение именно проверки
полного source-индекса, не правило упаковки будущих неполных пакетов.
Цикл depends_on блокирует проверку согласованности source-каталога; обход
итеративный, без зависимости от лимита рекурсии Python. Замыкание выбора
содержит только depends_on: derived_from/implements/validated_by/supersedes
не превращаются в исполняемые зависимости и не объявляют успешный прогон.
Каждый файл выбранного замыкания сверяется с размером/SHA-256. Метаданные ссылок
сопоставляются со свидетельством, но физическая цепочка этим API не обходится.

## Результат и диагностика
API возвращает dict: schema_version=1, layer=catalog_binding_and_graph,
status=passed_known_inputs/blocked_known_scope/failed/unsupported, source_consistency=
mutable_tree_observations, inputs с наблюдаемыми path/SHA-256/размерами,
selected_closure, checked_artifacts, unreferenced_approvals, diagnostics,
not_checked. Успех относится к точным переданным байтам, не к последующему
состоянию source-дерева. Обнаружение одной ошибки прекращает этот проход;
в отчёте остаются только фактически выполненные части. Ошибка/недоступность
движка/неподдержанные события не превращаются в успех или skip.

Во ВСЕХ результатах overall_admission=not_evaluated, transition_allowed=false.
Это намеренная граница, а не разрешение на полномочия: слои получения данных,
полноты событий, неисполненной scoped-семантики ограничений, покрытия ядра, совместимости среды,
выпуска и активации перечислены как непроверенные. Имя status нельзя использовать
как общий допуск. Общий report-контракт и полный валидатор ещё не завершены.

Диагностика содержит стабильный код без содержимого/частного абсолютного пути.
Логические пути попадают в inputs только после структурной проверки имени.
Отчёт локален: его публикация/экспорт не разрешаются автоматически, как и
передача метаданных symlink с частными целями. Во входы и отчёты не добавляются
временные метки имён. Библиотека не пишет исходники, не меняет решения/связку.

Лимиты: 10000 переданных файлов, 16 MiB на blob, 64 MiB суммарно, 10000 версий,
50000 отношений. Превышение даёт отказ. Это пределы текущей реализации,
не заявление о проверенной поддержке максимальной нагрузки.

## Проверка и применение
Из корня репозитория, в разрешённой среде:
../.venv/immutable-agent-system/bin/python agent_system/validation/ent-0006/r0003/verify.py
Общий прогон: ../.venv/immutable-agent-system/bin/python tests/run-all.py.
Все 34 теста должны пройти без failures/errors/skips. Ненулевой код или
прерывание не дают успешного результата. Фикстуры изолированы и синтетические;
Linux-интеграция использует доверенный текущий checkout и объявленные expected,
не подтверждает безопасность произвольного чужого дерева или его полноту.

Испытаны цепочка, ромб, цикл, граф на 1001 версии, точная пропущенная ревизия,
ошибки идентичностей, путей, решения, состава и байтов, множество файлов,
порядок файлов и links, несвязанные события, ошибки парсера/движка, отсутствие
сети/мутации входов, закрытый общий допуск. Поддержка событий ограничена ENT-0007 r0001: release-события и семантические
коррекции не поддержаны; при неизвестном влиянии переход заблокирован.

## Приобретение входов в этой ревизии
Алгоритм check.py побайтово совпадает с r0002; изменилась точная зависимость
на файловый слой и интеграционная проверка. verify.py теперь получает ожидаемый
набор через ENT-0005 r0003 read_set: один закреплённый корень, инвентарь решений
до/после, затем binding/graph/scoped-events. Производственный API check_catalog
по-прежнему принимает bytes, не перечисляет source и не скрывает границы.
Evidence файлового слоя остаётся отдельным результатом, не разрешением.
Подготовка ожиданий в тесте доверяет checkout; нельзя применять её как
самоподтверждение неизвестного чужого дерева. Подлинность исходного плана
и общий формат отчёта — отдельные ещё не завершённые обязанности.
