# ENT-0013 r0001 — точный неполный кандидат и покрытие ядра

## Назначение и граница

Универсальный protocol для самоприменимой `agent_system`, не событие выпуска,
не формат допуска совместимого выпуска и не разрешённый экспортный пакет.
Источник — задание владельца о системе B, ядро ENT-0001 r0001 и ранее данное
условное делегирование внедрения после проверок. Это summary основания,
не новая прямая цитата владельца об этих байтах. Частная архитектура, built-in
инструкции и данные исходной среды сюда не извлекаются.

Нормативная машиночитаемая таблица — [candidate.json](candidate.json).
[check.py](check.py) проверяет её ограниченную согласованность;
[verify.py](verify.py) содержит тесты этого checker. Тексты правил остаются
в собственных версиях ENT-0001/0011/0012; здесь ссылки и производный snapshot
метаданных, а не второй редактируемый индекс или копия ядра.

`readiness=incomplete_candidate`; compatible_release/export/activation и
transition_allowed всегда false. Изменить эти флаги или заменить профиль
для получения допуска нельзя: r0001 это отвергает. `consistent_incomplete_candidate`
означает только согласованность точного неполного описания с известными входами.
Ни approval этой сущности, ни PASS её тестов не утверждают полноценное покрытие,
совместимость, выпуск, экспорт или активацию.

## Точный состав и исключение самоссылки

Корни payload — ENT-0012 r0001 и ENT-0010 r0001. Их depends_on closure:

| ENT | Ревизия |
|---|---|
| 0001 | r0001 |
| 0002 | r0003 |
| 0003 | r0002 |
| 0004 | r0002 |
| 0005 | r0003 |
| 0006 | r0003 |
| 0007–0012 | r0001 каждая |

Всего 12 ревизий / 34 нормативных артефакта. `components` фиксирует полные
выбранные revision records: subject, title, kind, scopes, artifacts, relations,
approval reference и provenance. Сравнение с переданным индексом точное по
разобранному JSON (порядок object keys/пробелы не значимы, типы чисел различимы).
Каждый артефакт затем связан с bytes/hash/size и approve_revision прежним
ENT-0006 r0003. Нельзя выбирать latest, добавлять/терять component, заменять
ревизию или считать наличие одной корневой сущности достаточным.

**ENT-0013 r0001 — descriptor снаружи описываемого payload.** Его четыре
артефакта и approval учитываются обычным registry отдельно. Ни сам descriptor,
ни его approval не добавляются рекурсивно в собственный payload. Это узкое
разделение envelope/payload, не готовый формат переносимого выпуска.

Hash всего registry намеренно не входит в candidate: регистрация самого
candidate изменила бы hash и создала цикл. Вместо этого неизменные выбранные
records фиксируются здесь, а **полный индекс и известный ledger фиксируются
отдельно для каждого запуска** прежними plan/acquisition средствами ENT-0008/0009.
Добавление ENT-0013 в индекс не меняет frozen records. Новые известные
ограничения должны подаваться при новом запуске; старый snapshot не заменяет
актуальный набор решений. Их глобальная полнота и подлинность не доказаны.

## Чтение покрытия

G01–G07 / W01–W09 — локальные имена соответствий двум группам пункта 1
раздела «Требования к ядру» ENT-0001 r0001. Это не изменение ядра. `core_item=1`
и exact core subject/hash задают исходное место; локальные labels — краткие
наименования, не цитаты. C02–C10 отдельно ссылаются на пункты 2–10 того же
раздела через `core_item`. Так не теряются условия допуска вне списка способностей.

Каждая строка имеет clauses (exact subject/path/полный heading), checks
(exact subject/path/locator, заявленный уровень и `result=defined_only`) и
непустые gaps. `test` locator — имя определения функции в AST, не запуск;
`scenario` — case_id в закреплённом JSON с model_review и behavior=false.
Уровень `document_structure` означает структуру документа/данных;
`bounded_fixture_execution` — определённый fixture-тест ограниченного механизма;
`model_review` — разбор модели. Здесь ни один из них не выдаётся за наблюдение
реального агента или целевой среды. Сопутствующий check строки **не является
достаточным тестом всего её смысла**, особенно C02–C10. Checker проверяет
расположение определений, но не верность заявленного уровня/содержательного
соответствия. Структурная ссылка на AST не доказывает даже достижимость кода.

Краткий указатель к основной таблице (полные refs/checks/gaps — в JSON):

| Строки | Состояние | Основной оставшийся пробел |
|---|---|---|
| G01 | partial | Нет сквозного менеджера изменения/связок |
| G02 | partial | Точный граф не обновляет активную связку |
| G03 | partial | Нет release events/authentication/global completeness |
| G04 | partial | Freeze подготовки — не exporter/публикация |
| G05 | specified_only | Реальная адаптация новой среды не выполнена |
| G06 | partial | Локальные проверки не дают общего допуска |
| G07 | specified_only | Нет manager/практики явной активации |
| W01–W09 | model_only | Поведение агента не проверено |
| C02–C10 | partial | Требования релиза/среды/полномочий не исполнены этим descriptor |

Перечислены **пробелы**, а не обещание полноты их выявления. JSON содержит
16 capability rows и 9 отдельных condition rows. Для каждого сохранён
непустой gap; ни одна строка не имеет complete. Истинность claim/достаточность
покрытия и полнота перечисленных пробелов требуют отдельной содержательной
проверки и здесь `not_checked`, а не автоматически PASS.

## Контракт checker и процедура запуска

Установка инструментов доверенная, отдельная от source и недоступная ему для
записи. До использования check.py вызывающий проверяет его происхождение и
точные bytes по отдельно доверенному основанию ENT-0013. Вход не выбирает
путь установки/код. Три entry pins ENT-0009 и его 21 transitive pins проверяются
через прежний loader; сохраняется ограничение check→runpy TOCTOU при атакующем,
способном одновременно писать в установку. Hash не является подписью.

API:

```python
check_candidate(candidate_bytes, expected_candidate,
                registry_blob, decisions, payloads)
```

- `candidate_bytes`: bytes UTF-8 без BOM, LF и ровно один завершающий LF;
  strict JSON без повторных ключей/не-JSON constants. `expected_candidate`:
  внешние sha256/size_bytes, не вычисленные из недоверенного входа как источник доверия.
- `registry_blob`: отдельные bytes полного индекса этого запуска, а не frozen records
  вместо индекса. Caller отдельно фиксирует pin индекса и known ledger/контекст
  запуска; новый checker сам не аутентифицирует/не читает эти источники.
- `decisions`: path→bytes всех объявленных известных решений этого запуска,
  без скрытого выбора только положительных/использованных событий.
- `payloads`: path→bytes **ровно 34 selected артефактов**, не всех исторических
  артефактов registry и не descriptor. Лишние/недостающие пути запрещены.
- Контекст только `validate / agent_system.candidate`, явные корни и complete
  closure. Проверка ограничений этой области не заменяет проверки export/activation.

Порядок: проверить внешний pin → доверенный loader → strict разбор и закрытый
профиль → frozen records/точные пути → ENT-0006 binding/known scope → точный
closure/core hash → 16+9 rows, ссылки и постоянно закрытые gates. Если scope
заблокирован, возвращается blocked_known_scope; неподдержанные данные/инструменты
дают unsupported либо failed. При любом результате флаги переходов false.
Положительный результат содержит только перечень ограниченных consistency checks
и blocker id/count, а не per-capability результаты исполнения. Готового CLI
для произвольного source/архива нет; это функция над уже явно переданными bytes.

Запуск в подготовленной изолированной среде jsonschema+обязательных зависимостей:

```sh
python agent_system/candidates/ent-0013/r0001/verify.py
python tests/run-all.py
```

Fixture discovery из trusted checkout в verify.py — исключительно тестовый
сбор известных входов, не способ аутентифицировать произвольную чужую среду.
Для практического наблюдения использовать прежний reader под одним root fd,
явные внешние ожидания и inventory ledger; новые записи local сохранять вне Git.
Сам checker source не читает, данные не пишет, код из inputs не выполняет,
не вызывает prepare/export/activate. Per-input limit 16 MiB, всего 64 MiB
registry+decisions+payloads, до 10000 entries; candidate отдельно до 16 MiB.
Глубокие/некорректные данные отклоняются; resource/authentication/atomicity
обещания прежних компонентов не расширяются.

## Изменения и оценка решения

Выбран snapshot выбранных records. Альтернатива pin всего registry здесь
отвергнута из-за self-hash cycle; альтернативный новый release-формат отложен,
поскольку модель разрешения/публикации ещё не реализована и не проверена.
Плюсы: явные версии/refs/пробелы, повторное использование проверенного binding,
нет latest/дублирования правил/новых библиотек или обхода известного запрета.
Минусы: поддержание ссылок и ручная содержательная оценка; JSON metadata snapshot
объёмен и не служит самостоятельным доказательством. Это обоснование архитектуры,
не измерение превосходства по скорости над альтернативами.

Риски: stale/неполный ledger, недоверенный внешний pin, ложные coverage claims,
переоценка AST/fixtures, TOCTOU установки. Они явно не закрыты. Новое содержание,
компонент/корень/claim/метод требует новой immutable revision candidate и нового
run с отдельными ожиданиями индекса/решений. Старые records/байты не переписываются;
новая версия сама не отзывает старую. Правило самоприменимо к ENT-0013: его
изменение проходит тот же учёт/согласование/проверки, без рекурсивного самоодобрения.
Влияние: появляется управляемое неполное описание текущего payload и проверяемая
traceability, но exporter, binding manager, release permissions, реальная адаптация,
проверка поведения и явная активация от этого не появляются.
