## 3. Исследования

### 3.1. Как это решают в документации эксплуатации

- **Google Markdown Style Guide:** «используйте явные пути для ссылок внутри
  Markdown», «избегайте относительных путей, кроме ссылок внутри того же
  каталога». Прямо не рекомендует конструкции, ведущие на два-три уровня вверх через `../` —
  а именно они сейчас в `algorithm.md` (`../../../tools/scripts/...`).
- **Runbook best practices (incidenthub, inoc):** «добавляйте ссылки на
  артефакты автоматизации», «если команд много и они идут подряд — вынесите их
  в скрипт и дайте ссылку на файл», «ссылки на инструменты и данные» названы
  отдельным обязательным блоком ранбука.
- **Согласованность и предсказуемость путей** в runbook-практике считается
  самостоятельной ценностью: шаблон пути `{...}/{...}` снижает число ошибок
  при ручном выполнении.

Вывод: и «ссылка на каждый артефакт», и «единая система отсчёта пути» —
устоявшаяся практика, а не изобретение под этот репозиторий.

### 3.2. Существует ли готовая утилита

Проверено: `command -v lychee`, `command -v markdown-link-check` — **обе
отсутствуют** в среде.

- **lychee** (Rust, Apache-2.0, есть GitHub Action) — быстрый асинхронный
  проверщик ссылок в Markdown/HTML.
- **markdown-link-check** (Node) — то же, но в проектах от него уходят:
  Docker-образ тянется с Docker Hub анонимно и ловит лимит 429, из-за чего
  падают посторонние PR (PR mondoohq/mql#11844, октябрь 2026).

**Запрос к заказчику по правилу 7.2.** Обе утилиты закрывают только ту часть
задачи, которая уже закрыта: проверку, что цель ссылки существует — её делает
`test_repo.py` [6] на Python без внешних зависимостей (241 ссылка, 0 битых).
Ни одна из них **не умеет** того, что составляет суть задачи: проверить, что
каждая названная в шаге сущность снабжена ссылкой, что у шага есть перечень
средств и что база пути объявлена. Это знание о структуре наших документов,
внешней утилите оно недоступно.

Предлагаемое решение: **не добавлять бинарную зависимость**, расширить
существующие проверки. Если заказчик хочет именно lychee — это отдельное
решение, и оно не отменяет ни одного пункта правила ниже.

## 4. Предложение: правило навигации

Состав — шесть пунктов. Пункты П1—П4 задают формат, П5—П6 закрепляют его
проверкой.

### П1. Префикс базы пути

Каждый путь к сущности начинается префиксом, который объявляет систему отсчёта:

| Префикс | Откуда считается | Пример | Соответствие в репозитории |
|---|---|---|---|
| `VENTOY:/` | корень раздела Ventoy (exFAT) | `VENTOY:/ISO/windows/en-us_...iso` | `ventoy-partition/…` |
| `TOOLS:/` | корень раздела Tools (NTFS) | `TOOLS:/scripts/apply-blocking.ps1` | `tools/…` |
| `BUILD:/` | каталог текущей сборки | `BUILD:/answer/autounattend-ltsc-2024.xml` | `ventoy-partition/builds/<станция>/…` |
| `REPO:/` | корень репозитория | `REPO:/research/07-blocking-mechanisms.md` | как есть |
| `SYSTEM:` | команда или путь ОС, не сущность флешки | `SYSTEM:slmgr /dlv`, `SYSTEM:C:\Windows\Panther\` | не проверяется |

Первые четыре — проверяемые: по префиксу путь однозначно раскрывается в путь
репозитория и сверяется с диском. Многоточия в пути запрещены.

### П2. Каждая наша сущность в шаге — markdown-ссылка

Первое упоминание сущности в шаге оформляется ссылкой на её расположение
в репозитории:

```
[`apply-blocking.ps1`](../tools/scripts/apply-blocking.ps1)
```

Ссылка ведёт на файл в репозитории — это единственный адрес, который можно
проверить. Путь на флешке даётся рядом префиксом из П1, потому что на флешке
`tools/` и `builds/` лежат на разных разделах.

Внешние сущности (Ventoy, `diskpart`, `DISM`, `slmgr`, `pnputil`) ссылками не
оформляются и помечаются `SYSTEM:`.

### П3. Раздел «Средства» в каждом шаге

Между «Сеть» и «Действия» добавляется таблица:

```
**Средства.**

| Сущность | Тип | Путь на флешке |
|---|---|---|
| `export-drivers.ps1` — со ссылкой | скрипт | `TOOLS:/backup/initial_backup/scripts/export-drivers.ps1` |
| `disk-image.sh` — со ссылкой | скрипт | `TOOLS:/backup/disk_image/scripts/disk-image.sh` |
| `diskpart` | средство ОС | `SYSTEM:` |
```

Колонка «Путь на флешке» обязательна: по ней мастер открывает файл на носителе,
не открывая репозиторий.

### П4. Сводная карта сущностей в начале алгоритма

Один раздел после «Порядок шагов» со всеми сущностями алгоритма и номерами
шагов, где они применяются. Это единственный экран, по которому можно собрать
чемодан на выезд.

### П5. Проверка в `repo-validate` и в тестах

| Параметр проверки | Как считается |
|---|---|
| У каждого шага есть раздел «Средства» | заголовок или выделенная строка внутри `### Шаг N` |
| Каждая наша сущность в шаге есть в его таблице средств | сопоставление имён файлов из текста шага со строками таблицы |
| Каждая сущность из таблицы средств имеет рабочую ссылку | разбор markdown-ссылок и `os.path.exists` |
| Каждый путь с префиксом разрешим | раскрытие `VENTOY:/`→`ventoy-partition/`, `TOOLS:/`→`tools/`, `BUILD:/`→каталог сборки, `REPO:/`→корень |
| Многоточий в путях нет | поиск `\...` и `/...` вне блоков кода с комментарием |
| Префикс без пути не употребляется | `TOOLS:/` без продолжения — ошибка |

### П6. Шаблон

`ventoy-partition/builds/_templates/algorithm.md` приводится к тому же формату,
иначе следующий билд будет написан по-старому.

## 5. Что правило даёт проверкам

Сейчас «сущность названа, но пути нет» не ловится ничем. После введения
правила это машинная проверка: список имён файлов в шаге сравнивается со
строками его таблицы средств, а каждый путь раскрывается и сверяется с диском.
Тот же механизм закроет класс ошибок, который уже случался: алгоритм ссылается
на сущность, которой нет (Этап 10, находка F1 — шаг 5 расходился с файлом
ответа).

**Правило соблюдено там, где оно обязательно**: `algorithm.md` сборки и
шаблон проходят все проверки `test_navigation.py` — раздел «Средства» в каждом

Причина, по которой 205 путей остались без префикса, содержательная: `PLAN.md`,
`research/` и `README.md` описывают **репозиторий**, а не флешку, и их пути
считаются от корня репозитория однозначно. Неоднозначность, ради которой
вводилось правило, возникает только там, где один текст описывает два раздела
флешки одновременно — то есть в `algorithm.md`.

Расширять ли префиксы на все 44 документа — отдельное решение: это правка
205 записей без изменения смысла и выигрыш только в единообразии.
