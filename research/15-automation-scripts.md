# 15. Скрипты автоматизации

Этап 5, группа `tools/scripts/`. AUDIT по правилу №1 (`CONVENTIONS.md` §7.1):
цель → исследование → систематизация → паттерны. Реализация не начата — по
правилу №2 нужны решения владельца.

**Дата исследования:** 2026-10-14.

## 1. Цель

`PLAN.md`, Этап 5, заявляет:

- `scripts/windows/` — PowerShell: подготовка ПК, чистка, драйверы, AD/GPO,
  отчёты;
- `scripts/linux/` — bash: диагностика, восстановление, бэкап;
- `scripts/flash/` — обслуживание самой флешки;
- общие правила: идемпотентность, `-WhatIf`/`--dry-run`, логирование в файл,
  запрет деструктивных операций без явного флага.

Задача AUDIT — понять, что из этого уже сделано, что реально нужно под
станционный алгоритм, и какие паттерны обязательны.

## 3. Разделение «универсальное против станционного» уже записано

Конфликта между `tools/scripts/` и `builds/<станция>/scripts/` нет — они
описаны как разные вещи:

- `ventoy-partition/builds/README.md`: `scripts/` — «станционно-специфичные
  скрипты»;
- `PLAN.md`: `tools/scripts/` — «Наши наработки: PowerShell, bash, обслуживание
  флешки».

То есть **универсальное** (работает на любой станции) — в `tools/scripts/`,
**станционное** (значения под 8 ГБ распаянной памяти, конкретный NVMe,
конкретная политика) — в сборке станции. Шаг 8 станционного алгоритма ссылается
на «скрипты из `scripts/`» — это каталог **сборки**, и он сейчас пуст.

## 4. Что именно автоматизировать

Источник — станционный алгоритм, шаги 8, 9, 10 и 12, и систематизация из
`research/06-services-blocklist.md`.

### 4.1. Алгоритм применения уже написан в исследовании

`research/06-services-blocklist.md` задаёт готовый порядок из девяти шагов:

```
1. Аудит:  дамп служб, задач, Run/Active Setup, IFEO, GPO, WMI-subscriptions → отчёт
2. P0:     самовосстановление WU + provisioned appx + Active Setup + ContentDeliveryManager
3. P1a:    задачи планировщика
4. P1b:    службы-инициаторы
5. P2:     исполнители + IFEO-заглушки
6. T:      wrapper'ы точечных запретов
7. P3:     ситуативные — по профилю владельца
8. Enforcement-задача (паттерн P5) + лог
9. Контроль: повторный аудит → diff с шагом 1 → отчёт
```

Это буквально структура скриптов: **аудит → применить → контроль с diff**.

### 4.2. Обратимость обязательна, и она уже расписана

Там же — таблица «применили / откатили» для каждого механизма:

| Применили | Откат |
|-----------|-------|
| `Set-Service X -StartupType Disabled` | `Set-Service X -StartupType <исходное из дампа>` |
| `schtasks /Change /TN X /Disable` | `schtasks /Change /TN X /Enable` |
| `Remove-AppxPackage` | Переустановка из образа/Store |
| Ключ IFEO | `reg delete ...\Image File Execution Options\<exe>` |
| Ключ политики | `reg delete` / `Remove-ItemProperty` |
| ACL Deny | `icacls <путь> /remove:d <субъект>` |
| Запись в `hosts` | Удаление строки |
| Правило firewall | `Remove-NetFirewallRule -DisplayName ...` |

И прямое требование: **«Исходные значения обязательно фиксируются дампом на
шаге 1 — без него откат невозможен»**. Это означает, что скрипт аудита — не
отчёт «для галочки», а входные данные для отката.

### 4.3. Валидация — готовый чек-лист на 12 пунктов

Раздел 5 станционного алгоритма — таблица из 12 проверок с командами и нормами:
телеметрия, **работа Центра обновления**, службы из блэклиста, задачи,
проблемные драйверы, Wi-Fi/Bluetooth, TRIM, гибернация, pagefile, целостность
хранилища, **переживание перезагрузки**, бэкап.

Пункты 2 и 11 помечены обязательными: `AllowTelemetry = 0` ломает Центр
обновления на части редакций, а механизмы самовосстановления возвращают
значения после перезагрузки.

Это прямой кандидат в скрипт: те же 12 проверок, те же нормы, результат — в
`reports/` станции.

### 4.4. Enforcement-задача (паттерн P5)

`research/03-patterns.md`, P5: вместо борьбы с каждым случаем возврата —
собственная задача планировщика, которая периодически возвращает целевое
состояние и пишет лог отклонений. Параметры: запуск от SYSTEM, при старте с
задержкой около 2 минут и далее раз в 6 часов, идемпотентна, лог в файл.

Ценность для выезда: лог — готовый артефакт для отчёта «почему мусор вернулся».

### 4.5. Оптимизация под SSD и 8 ГБ ОЗУ (шаг 10)

Конкретные команды уже в алгоритме: `powercfg /hibernate off` (заодно убирает
Fast Startup), `fsutil behavior query DisableDeleteNotify` ожидается 0,
pagefile **не отключать**, а зафиксировать размер. Свободное место — не менее
10–15%.

## 5. Паттерны из внешних источников

### 5.1. Win11Debloat сознательно отказался от автоматического отката

Это самая полезная находка этапа. В проект был внесён PR «автоматический откат
реестра при сбое выполнения» (PR #613 к issue #612), реализован, а затем
**отклонён** с формулировкой:

> «An unattended rollback isn't a reliable safety net for the failure mode it
> exists to catch. An unattended rollback can hit the same access-denied
> failure that broke the apply in the first place, so it isn't a reliable
> safety net for the failure mode it exists to handle. Reverting registry state
> without asking is also not a call the script should make on the user's
> behalf. On failure, point to the pre-execution backup and the existing
> Restore Backup option instead of attempting the revert automatically.»

То есть: откат без спроса может упасть по той же причине, по которой упало
применение, и принимать решение об откате реестра за пользователя скрипт не
должен. Правильное поведение — **указать на дамп и команду восстановления**.

Отдельно отмечен дефект той же логики: восстановление удаляет поддерево ключа
перед перезаписью и не имеет собственного отката при частичном сбое — то есть
«спасательный» путь сам способен потерять данные.

Прочее по Win11Debloat, что надо учитывать:

- каталог `Regfiles/Undo/` — по `.reg`-файлу на каждое изменение;
- с релиза 2026.05.10 делается резервная копия реестра до изменений;
- **удалённые приложения резервной копией реестра не возвращаются** — только
  переустановка из Store или `winget`; исключения, которые сложно вернуть, —
  сам Microsoft Store и `XboxSpeechToTextOverlay`;
- параметры: `-Silent`, `-RunDefaults`, `-CreateRestorePoint`, `-Sysprep`,
  `-LogPath <файл>`;
- применяет локальные групповые политики, из-за чего Windows показывает
  «Управляется вашей организацией» — владельца надо предупреждать заранее.

### 5.2. LGPO.exe — есть, бесплатный, в manifest не внесён

`research/07-blocking-mechanisms.md` называет `LGPO.exe` инструментом переноса
локальных политик в рабочей группе, но в `manifest.csv` его нет — это пробел.

Что известно:

- распространяется Microsoft в составе **Security Compliance Toolkit**,
  страница загрузки `microsoft.com/en-us/download/details.aspx?id=55319`,
  файл `LGPO.zip`;
- лицензия — **Proprietary (Freeware)**, «there is no licensing fee associated
  with this technology»;
- доступен через `winget install -e --id Microsoft.SecurityComplianceToolkit.LGPO`;
- `LGPO.exe /b <путь>` — резервная копия локальной политики. Это штатный
  механизм отката для слоя GPO, которого нет у правки реестра напрямую.

Точный текст лицензионных условий Microsoft по первоисточнику **не проверен** —
сайт недоступен из рабочей среды.

### 5.3. PSScriptAnalyzer — статический анализатор, которого нам не хватает

Около 71 встроенного правила. Значимое для нас:
`UseShouldProcessForStateChangingFunctions` — **всегда включено**, severity
Warning, и оно ловит функции с глаголами `New`, `Set`, `Remove`, `Start`,
`Stop`, `Restart`, `Reset`, `Update` без `SupportsShouldProcess`.

Запуск: `Invoke-ScriptAnalyzer -Path <скрипт> -Severity Warning -EnableExit` —
код возврата отражает число замечаний, то есть годится для автоматической
проверки. Настройки — `PSScriptAnalyzerSettings.psd1`.

**Проблема:** PowerShell в рабочей среде отсутствует, и ни один `.ps1` за всю
работу не был выполнен ни разу. Анализатор здесь не запустить. Всё, что можно
сделать в репозитории, — собственные проверки в `tests/test_rules.py` (они уже
есть: `#Requires`, `CmdletBinding`, `$ErrorActionPreference`, `Start-Transcript`,
`-Append`) плюс документированная необязательная проверка для машины, где
PowerShell есть.

### 5.4. Общие требования к PowerShell-скриптам

Сводится к тому, что у нас уже принято, плюс несколько уточнений:

- `param()` — первым исполняемым оператором, до всего остального;
- `[CmdletBinding(SupportsShouldProcess)]` даёт `-WhatIf` и `-Confirm`
  автоматически;
- `Set-StrictMode -Version Latest` ловит необъявленные переменные — **у нас
  этого нет ни в одном `.ps1`**;
- **cmdlet'ы по умолчанию бросают non-terminating ошибки**, которые не попадают
  в `catch`. Нужен явный `-ErrorAction Stop` на строке, которую хочется поймать,
  либо `$ErrorActionPreference = 'Stop'` на весь скрипт (у нас второе);
- для внешних программ (5.1) успех определяется по `$LASTEXITCODE`, а не по
  `$?`;
- идемпотентность достигается проверкой состояния перед изменением и
  предпочтением `Set-*` перед `Add-*`;
- `Write-Host` — не логирование; `Start-Transcript -Append` — страховка, которая
  ловит и вывод внешних команд;
- коды возврата: `0` успех, `1` общая ошибка, `2` ошибка параметров или
  зависимостей, `3` не найдено. Это ровно наша схема.

## 6. Паттерны для внедрения

1. **Сначала дамп, потом изменения.** Скрипт аудита — входные данные для
   отката, а не отчёт. Требование прямо из `06-services-blocklist.md`.
2. **Никакого автоматического отката при сбое.** Указать на дамп и команду
   восстановления. Обоснование — решение сопровождения Win11Debloat (§5.1).
3. **Идемпотентность через проверку состояния.** Повторный запуск даёт тот же
   результат; `Set-*` вместо `Add-*`; перед изменением — прочитать текущее.
4. **`ShouldProcess` на всех изменяющих операциях**, чтобы `-WhatIf` работал
   не только как флаг, а реально ничего не менял.
5. **Лог в файл обязателен, коды возврата — для машины.** Уже правило проекта.
6. **Контроль — повторный аудит и diff с первым**, а не «всё применилось,
   значит хорошо».
7. **Enforcement-задача пишет лог отклонений** (P5) — это артефакт для отчёта.
8. **`Set-StrictMode -Version Latest`** добавить в правило проекта — дешёвая
   защита от опечаток в именах переменных.

## 7. Рекомендации

1. **`tools/scripts/flash/` не создавать.** Закрыть пункт плана ссылкой на
   корневой `scripts/check-flash.*`. Копия — это два места для одного факта.
2. **Основа — три скрипта под порядок из исследования:**
   `system-audit` (дамп до/после + diff), `apply-blocking` (порядок P0 → P1a →
   P1b → P2 → T → P3 → enforcement), `validate-system` (12 пунктов раздела 5
   алгоритма).
3. **`tune-ssd-ram`** — отдельным скриптом: команды шага 10 конкретные и
   проверяемые, смешивать их с блокировкой телеметрии не стоит — у них разные
   последствия ошибки и разный откат.
4. **`tools/scripts/linux/` наполнять только тем, что работает в Live-сессии.**
   Live Linux Mint — среда для диагностики и бэкапа; часть уже закрыта
   (`verify-backup`, `disk-image`). Новый скрипт нужен, только если он закрывает
   то, чего там нет.
5. **`LGPO.exe` внести в `manifest.csv`** в `os/windows/gpo_lock/` как
   запланированную сущность: он бесплатный и закрывает откат слоя политик.
6. **Добавить `Set-StrictMode -Version Latest` в `CONVENTIONS.md` §5** и в
   проверки `test_rules.py`.
