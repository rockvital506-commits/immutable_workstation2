# AUDIT наполнения TOOLS: 23 planned-строки, структура дерева, версии

Дата: 2026-10-15. Фаза AUDIT по `CONVENTIONS.md` §11.1.

Проверяемое утверждение: «раздел Tools наполнен сущностями в соответствии с
`CONVENTIONS.md` §4 и деревом группы → подкатегории → утилиты». Источники
обязательства: `CONVENTIONS.md` §4 и §10.1, `PLAN.md` (Этап 4), решение
заказчика о правиле комплектования TOOLS, факт носителя (NTFS 128 ГБ).

## 2. Находки

### N1. Версия Sophia Script в манифесте отстаёт на мажорный выпуск

В `manifest.csv` строка `Sophia_Script` имеет `version=7.3.0`. Запрос
`api.github.com/repos/farag2/Sophia-Script-for-Windows/releases/latest`
возвращает `tag_name = 8.0.0`, `published_at = 2026-10-11`.

Расхождение мажорное: 7.x против 8.0.0. Для инструмента, который точечно
правит политику и телеметрию, смена мажорной версии означает смену набора
команд и, возможно, отказ от части ключей. Строка добавлена 2026-10-10,
выпуск 8.0.0 вышел 2026-10-11 — на следующий день.

Остальные семь GitHub-утилит сверены тем же запросом и совпадают:
`smartmontools` RELEASE_7_5 ↔ 7.5, `stress-ng` V0.22.01 ↔ 0.22.01,
`WinUtil` 26.10.07 ↔ 26.10.07, `Win11Debloat` 2026.08.24 ↔ 2026.08.24,
`RustDesk` 1.5.0 ↔ 1.5.0, `iperf3` 3.22 ↔ 3.22, `VeraCrypt`
VeraCrypt_1.26.29 ↔ 1.26.29.

`fix_target = state`. Остальные 15 утилит берутся не с GitHub; их версии в
этом AUDIT не сверялись, потому что источник недоступен из среды проверки.

### N2. Поле version содержит значения, которые версией не являются

Четыре строки:

| Утилита | `version` | Что должно быть |
|---|---|---|
| `LGPO` | `PENDING` | версия Security Compliance Toolkit, откуда берётся `LGPO.exe` |
| `Autoruns` | `unversioned` | версия из `Autoruns.exe` |
| `ProcessExplorer` | `unversioned` | версия из `procexp.exe` |
| `SDIO-drivers` | `unversioned` | дата снимка пака драйверов |

`CONVENTIONS.md` §4 определяет поле как «Версия». Значений `unversioned` и
`PENDING` в определении нет; `PENDING` в схеме закреплено только за `sha256`,
и только для `status=planned`. Здесь оно перенесено в другое поле по аналогии.

Для трёх Sysinternals-утилит версия объективно существует — она зашита в
исполняемый файл и публикуется в журнале изменений Microsoft. `unversioned`
фиксирует не факт, а то, что версию не посмотрели.

`fix_target = state` для трёх строк, у которых версия публикуется; для
`SDIO-drivers` — `decision`, потому что пак драйверов обновляется непрерывно. **Закрыто 2026-10-15:** пак снят с флешки, на носителе остаются только индексы SDIO, сущность из `manifest.csv` удалена — см. `research/23-license-scope.md`, N26. Поле `version` больше не заполняется, потому что строки больше нет. Исходное основание —пак драйверов обновляется непрерывно
и вопрос «какую дату считать версией» требует решения.

### N3. Все 23 утилиты без контрольной суммы, и перехода в present ничто не требует

Каждая из 23 строк имеет `sha256=PENDING` и `size_bytes=0`. `CONVENTIONS.md`
§4 это разрешает: «Строки со `status=planned` допускают `sha256=PENDING` и
`size_bytes=0`. Для `present`/`verified` оба поля обязательны».

Расхождение не в строках, а в отсутствии перехода: ни одно правило не
требует, чтобы строка когда-либо покинула `planned`, и ни одна проверка не
сообщает, сколько строк в этом состоянии. На флешке 23 бинарника без
контрольной суммы означают, что подмену или повреждение файла не обнаружить:
`scripts/check-flash.sh` сверяет только ISO (это зафиксировано как N1 в
`research/19-update-integrity.md`), а для утилит сверять нечего — суммы нет.

`fix_target = doc`: нужно правило о том, когда строка обязана стать
`present`, и счётчик `planned`-строк в отчёте валидатора.

### N4. Поле category у четырёх строк трёхуровневое, а дерево считает os/windows одной подкатегорией

`tools/os/windows/` содержит шесть каталогов — `activation`, `debloat`,
`gpo_lock`, `installation`, `tweaks`, `updates`. Для остальных восьми групп
такой уровень называется подкатегорией (`diagnostics/cpu`, `rescue/boot`).
Для `os` он называется утилитой-родителем, а настоящая подкатегория
спускается ещё на уровень.

Следствия, проверенные подсчётом:

- `test_stage10.py` считает подкатегории как все подкаталоги группы, поэтому
  `os/windows` входит в счёт как **один** элемент. Реальных подкатегорий
  26 + 5 = **31** (пять, потому что `windows` сам уже учтён).
- Утилита лежит на глубине три: `tools/os/windows/tweaks/WinUtil`, тогда как
  у остальных — на глубине два: `tools/diagnostics/disk/smartmontools`.
- `category` в манифесте повторяет эту асимметрию: 19 строк двухуровневые,
  4 трёхуровневые.

Источники, которые спорят: дерево «группы → подкатегории» из задания и
`CONVENTIONS.md` §4, где `category` определён как «путь категории от корня
раздела» без ограничения глубины, а примеры двухуровневые. Прямого запрета
трёх уровней нет, поэтому это расхождение структур, а не нарушение строки.

`fix_target = decision`: либо `os/windows/*` признаётся подкатегориями (тогда
`category` становится `os/windows` → не совпадёт с путём утилиты), либо
правило глубины записывается явно и счёт подкатегорий приводится к нему.

### N5. Четыре подкатегории без утилит не помечены, хотя для трёх других такая пометка есть

Семь подкатегорий не содержат ни одного каталога утилиты. Три из них говорят
об этом явно:

| Подкатегория | Пометка в README |
|---|---|
| `network/diagnostics` | «Утилит здесь **нет намеренно**» |
| `rescue/partition` | «Всё уже в Strelec» |
| `security/scanner` | «**Утилит здесь нет намеренно.** Причина лицензионная» |

Четыре не говорят:

| Подкатегория | Что фактически в README |
|---|---|
| `backup/drivers` | процедура `DISM /Export-Driver`, утилит нет |
| `backup/profiles` | состав копий и условия, утилит нет |
| `rescue/boot` | «Что уже есть в Strelec», утилит нет |
| `rescue/registry` | «Что уже есть в Strelec», утилит нет |

Основание пустоты у всех четырёх есть и оно законное — это процедуры, а не
средства, что соответствует решению заказчика «процедура вместо каталога».
Расхождение в оформлении: читатель, который знает про пометку «нет
намеренно», не найдёт её там, где она так же уместна. Паттерн уже
существует в трёх файлах, значит он проверяем.

`fix_target = state`.

### N6. У родительских разделов «Этап 4» и «Этап 7» нет отметки выполнения

Подэтапы 4.1–4.8 имеют ✅ — восемь из восьми. В разделе «Этап 4» нет ни
одного незакрытого чекбокса. В разделе «Этап 7» все три чекбокса закрыты
`[x]`, из них два перечёркнуты как отменённые решением заказчика. При этом
заголовки обоих разделов идут без ✅, тогда как остальные 19 разделов этапов
отмечены.

`fix_target = state`.

### N7. Каталоги-держатели скриптов не отличимы от подкатегорий по структуре

Пять каталогов `scripts` лежат внутри подкатегорий:
`backup/disk_image/scripts`, `backup/initial_backup/scripts`,
`drivers/export/scripts`, `firmware/bios/scripts`, и `tools/scripts/procedures`
на уровне группы. Они входят в счёт подкатегорий (26), хотя утилитами не
являются, и исключаются из обхода вручную — список исключений зашит в двух
местах: в `test_stage10.py` и в обходе `tools/` в `test_navigation.py`.

Расхождение: признак «это держатель скриптов, а не подкатегория» нигде не
объявлен, он восстанавливается по имени каталога. Новая подкатегория с
именем `scripts` молча изменит счёт, а подкатегория с другим именем и тем же
смыслом — нет.

`fix_target = doc`.

## 3. Поправки к прежним утверждениям

Два числа, которые назывались в рабочих сводках раньше, неверны:

- **«29 каталогов утилит против 23 строк»** — ошибка подсчёта. Обход
  принимал за утилиты подкатегории `os/windows/*`. Факт: каталогов утилит
  **23**, ровно по числу строк манифеста; расхождения состава нет.
- **«14 подкатегорий без бинарников»** — факт **7**, и у трёх из семи
  основание записано в README (см. N5).

## 4. Что не проверялось

- Версии 15 утилит не с GitHub: `CrystalDiskInfo`, `MemTest86Plus`, `Prime95`,
  `DMDE`, `NTPWEdit`, `LGPO`, `Nmap`, `Wireshark`, `WifiInfoView`,
  `MyPublicWifi`, три Sysinternals, `SDIO`, `SDIO-drivers`. Их источники
  недоступны из среды проверки.
- Доступность каждого из 23 URL не проверялась: загрузка файлов из среды
  проверки не выполнялась.
- Фактическое наличие бинарников на флешке не проверялось: все ISO и
  бинарники в репозитории — заглушки.
- Соответствие состава утилит правилу комплектования TOOLS (сначала Strelec)
  проверялось на Этапах 4.1–4.8 и здесь не перепроверялось.
