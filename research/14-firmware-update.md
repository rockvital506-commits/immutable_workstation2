# 14. Прошивки: BIOS/UEFI, диски, периферия

Этап 4.8, группа `tools/firmware/`. AUDIT по правилу №1 (`CONVENTIONS.md` §7.1):
цель → исследование → систематизация → паттерны. Реализация не начата — по
правилу №2 нужны решения заказчика.

**Дата исследования:** 2026-10-14.

## 1. Цель

Выездной мастер обновляет прошивки на станциях заказчика **без вскрытия
корпуса**, офлайн или с недетерминированным интернетом, на коммерческой основе.
Нужно понять: что реально прошиваемое, чем, и что из этого стоит держать на
флешке.

План (`PLAN.md`, п. 8 порядка наполнения): «`firmware/` — BIOS/UEFI, SSD/HDD,
прошивка сетевого оборудования».

## 2. Что показывает AUDIT: четыре независимых канала

Единого инструмента нет. Каналы не пересекаются ни по утилитам, ни по рискам,
ни по возможности отката.

| Канал | Чем шьётся | Откат | Риск при ошибке |
|-------|-----------|-------|-----------------|
| BIOS/UEFI материнской платы | Утилита вендора из UEFI (у MSI — **M-FLASH**) | Только бэкап SPI или кризисное восстановление | **Станция не загружается** |
| NVMe-накопитель | `nvme fw-download` + `fw-commit` | Слот прошивки, если их несколько | Диск может уйти в нерабочее состояние |
| SATA-накопитель | Утилита вендора, в Linux — `hdparm --fwdownload` | Обычно нет | Потеря диска |
| Периферия (EC, TPM, док-станции, USB-хабы) | `fwupd` + LVFS, если вендор там есть | Зависит от устройства | Обычно низкий |

### 2.1. BIOS/UEFI: канал вендора, не универсальный

MSI документирует M-FLASH как основной способ для работающей платы:
подготовить **FAT32**-носитель, распаковать архив, положить файл **в корень**
(не в подкаталог), войти в BIOS по `Del`, выбрать M-FLASH, подтвердить.
Второй способ — Flash BIOS Button, требует переименования файла в `MSI.ROM`
и отдельного помеченного USB-порта; для обычных M-FLASH переименование
**не нужно и вредит**: имя файла должно совпадать со строкой версии в BIOS.

DOS-путь (`afudos` и подобное) MSI тоже описывает, но он устарел и требует
загрузочного DOS-носителя — это отдельная категория `ISO/dos/`.

Intel FPT (`fptw64.exe`) — низкоуровневая запись SPI через ME-интерфейс.
Даёт полный бэкап (`fptw64 -d backup.bin`), запись регионов
(`-bios`, `-me`, `-gbe`), работает там, где M-FLASH не справился. Но:

- требует **соответствия версии FPT версии ME**;
- пишет напрямую в SPI, ошибка — это «кирпич», а не откат;
- на многих платах запись заблокирована Flash Descriptor / BIOS Lock
  (`Error 25: The host CPU does not have read access to the target flash area`);
- в WinPE нужен ручной `drvload HECI.inf`.

**Вывод:** FPT — инструмент восстановления и диагностики, а не штатный способ
обновления. Для выезда без вскрытия штатный путь — утилита вендора из UEFI.

### 2.2. NVMe: единственный канал с нормальным CLI

Стандартный поток — `nvme-cli`:

```bash
nvme list                                  # устройство и текущая FW Rev
nvme id-ctrl /dev/nvme0 | grep 'fr '       # версия прошивки
nvme fw-log /dev/nvme0                     # слоты прошивок
nvme fw-download --fw=<файл> /dev/nvme0    # загрузить в контроллер
nvme fw-commit --slot=2 --action=0 /dev/nvme0   # записать в свободный слот
nvme fw-commit --slot=2 --action=2 /dev/nvme0   # активировать
```

Значения `--action`: `0` — записать в слот без активации, `1` — активировать
с перезагрузкой, `2` — активировать без перезагрузки, `3` — активировать
немедленно. Поддерживается ли активация без сброса — видно в
`nvme id-ctrl -H /dev/nvmeX | grep 'Firmware Activate Without Reset Supported'`.

Ключевое преимущество перед BIOS: **слоты прошивок**. Если их несколько, новая
прошивка пишется в свободный слот и активируется — старая остаётся и может
быть возвращена. Это единственный канал прошивок в нашей задаче, где откат
штатный, а не аварийный.

Проблема не в инструменте, а в **получении файла прошивки**. Вендоры
распространяют его в виде Windows-утилит или EXE-инсталляторов; бинарник
часто приходится извлекать (`innoextract` для Lenovo/Kioxia, распаковка ZIP у
Crucial/WD). Готовых публичных каталогов бинарников нет.

`nvme-cli` **не входит** в состав Linux Mint по умолчанию — его нужно
устанавливать. Для офлайн-выезда это означает заранее скачанные `.deb`.
`smartmontools` в Mint, по данным источников, предустановлен, но это
диагностика, а не прошивка.

### 2.3. Периферия: fwupd + LVFS

`fwupd` — единственный унифицированный механизм: один CLI для UEFI-капсул,
NVMe, Thunderbolt, док-станций, TPM, EC.

Офлайн-режим документирован прямо в LVFS:

```bash
sudo fwupdmgr install /путь/firmware.cab    # локальный файл
fwupdmgr get-details ./firmware.cab          # посмотреть, не применяя
fwupdmgr get-devices                         # что вообще прошито
fwupdtool hwids                              # GUID'ы железа
```

`.cab` содержит подпись вендора, и `fwupd` её проверяет перед записью. Файлы
скачиваются на другой машине с `fwupd.org/lvfs/devices/` или у вендора.
Есть и режим «каталог в образе»: положить `.cab` в
`/usr/share/fwupd/remotes.d/vendor/firmware` и включить remote
`vendor-directory`.

Но для целевой станции это не работает: **MSI не публикует обновления
ноутбуков через LVFS**. На LVFS у MSI 13 файлов прошивок (UEFI Capsule), у
отдельной учётки «MSI (Notebooks)» — один файл, и это `ms15g2`, не B12M.
ArchWiki по MSI Modern 15 A11S формулирует прямо: «Some devices can be listed
with fwupd, but MSI does not provide updates via the LVFS».

`fwupd` остаётся полезным как **инвентаризатор**: `fwupdmgr get-devices`
показывает текущие версии прошивок всего, что он видит, даже если обновлений
нет. Это дешевле, чем собирать версии руками по утилитам вендоров.

## 3. Критичное ограничение нашей флешки

**M-FLASH не читает exFAT.** Это ломает всю схему.

Наш носитель (`README.md`): раздел 0 `Ventoy` **exFAT** 340.72 ГБ, раздел 1
`VTOYEFI` **FAT16** 32 МБ (служебный, не изменять), раздел 2 `Tools`
**NTFS** 128 ГБ.

Файл прошивки, положенный в `Tools:` или в ISO-раздел, M-FLASH не увидит.
Есть подтверждённый случай именно с Ventoy: BIOS видел только маленький
загрузочный раздел, а не основной, где лежал файл.

Документация MSI говорит «FAT32», практика сообщества расходится: часть
пользователей сообщает, что M-FLASH читает и NTFS, часть — что читает только
FAT32, причём иногда не видит конкретный носитель без видимой причины.
**Опираться на NTFS нельзя**: расхождение между официальной документацией и
сообществом слишком велико, а цена ошибки — незагружающаяся станция.

### Варианты решения

| Вариант | Что делать | Цена | Риск |
|---------|-----------|------|------|
| **A. Отдельная маленькая FAT32-флешка** | Держать в сумке флешку 1–8 ГБ, FAT32, только для прошивок | Вторая флешка в комплекте | Минимальный |
| **B. Переформатировать раздел Ventoy в FAT32** | Ventoy поддерживает FAT32 на первом разделе | exFAT → FAT32: лимит 4 ГБ на файл, требует кластер ≥ 2048; переформатирование **уничтожает ISO** | Средний: ISO придётся раскладывать заново |
| **C. Переустановить Ventoy с зарезервированным местом** | `Ventoy2Disk` → «Option → Partition Configuration» (или `-r` в Linux), затем создать Part3 в FAT32 | Переустановка Ventoy **уничтожает и ISO, и Tools** | Высокий |
| **D. Положить файл в `Tools:` (NTFS)** | Ничего | Ноль | **Непроверяемо**: часть плат не увидит |

Замечание по B: наши ISO — до 6 ГБ (Win11 LTSC), FAT32 их не примет. Вариант B
фактически отпадает, если только не переносить образы в `_scratch`.

## 5. Лицензии

| Средство | Статус | Для коммерческого выезда |
|----------|--------|--------------------------|
| M-FLASH | Встроен в BIOS MSI | Да, это функция платы |
| `nvme-cli` | Открытый исходный код (GPL) | Да |
| `fwupd` | Открытый исходный код | Да |
| Прошивки с LVFS | Подписаны вендором, распространяются вендором | **Не проверено** по первоисточнику |
| Intel FPT (`fptw64.exe`) | Часть Intel ME System Tools | **Не проверено**: публичные источники описывают как утилиту Intel для разработчиков и производителей, условий для сервисного выезда не нашлось |
| Файлы прошивок BIOS с сайта MSI | Собственность MSI | **Не проверено**: условия хранения на коммерческом носителе не найдены |
| Прошивки NVMe, извлечённые из EXE вендора | Собственность вендора | **Не проверено**, и сам способ извлечения спорен |

Отдельный вопрос: распространение утилит Intel FPT вне платформы Intel и
хранение скачанных прошивок на носителе мастера. Ни подтверждения, ни запрета
в первоисточниках найти не удалось — сайты вендоров из рабочей среды
недоступны.

## 6. BitLocker: обязательная приостановка

Обновление прошивки меняет измерения загрузки, запечатанные в TPM. Профиль
PCR по умолчанию на UEFI с Secure Boot — **PCR 7 и 11**; при такой привязке
обновление прошивки вендора (PCR 0) **терпимо**. Но если привязка ушла на
PCR 0, 2, 4, 11, обновление прошивки ломает печать, и станция уходит в
восстановление BitLocker. Проверить профиль можно одной командой
(`manage-bde`), а рекомендованное Microsoft действие однозначно:
**приостанавливать BitLocker перед обновлением прошивки TPM или UEFI** и
возобновлять после, `-RebootCount 0` или 2 и больше.

Это не теория: есть задокументированные случаи, когда после обновления BIOS
станция запрашивала ключ восстановления при каждой загрузке, а повторное
включение BitLocker блокировалось — помогал только сброс TPM.

Прошивки NVMe и контроллеров хранения тоже меняют порядок инициализации и
могут повлиять на измерения загрузки.

Это совпадает с уже принятым в проекте правилом приостанавливать BitLocker
перед снятием образа (`tools/security/encryption/`) — то есть приостановка
должна быть **однократной** на весь выезд, а не на каждую операцию.

## 7. Домашние роутеры и сетевое оборудование

Заявлено в плане, но исследовать почти нечего:

- прошивка роутера — это веб-интерфейс вендора и файл с его сайта, унификации
  нет;
- для офлайн-выезда нужен файл прошивки конкретной модели, которого у нас
  заранее нет;
- альтернативные прошивки (OpenWrt и подобные) — это отдельная задача с
  риском потери устройства и сменой гарантийного статуса.

Рекомендация: **из группы исключить**, оставив в алгоритме только пункт
«записать текущую версию прошивки роутера при диагностике сети».

## 8. Паттерны для внедрения

1. **Правило приостановки BitLocker одно на выезд.** Приостановить до первой
   операции с прошивками или образами, возобновить после проверки. Не
   приостанавливать по нескольку раз.
2. **Сначала инвентаризация, потом решение.** Записать версии BIOS, ME,
   дисков до любых изменений. Иначе нечем сверить результат и нечего искать.
3. **Прошивка — не по умолчанию, а по показанию.** Обновление BIOS меняет
   настройки UEFI (в том числе Secure Boot) и может откатить часть работы
   предыдущих этапов. Повод должен быть конкретным.
4. **Откат готовится до прошивки, не после.** Бэкап SPI (`fptw64 -d`),
   свободный слот прошивки NVMe, ключ восстановления BitLocker — всё до.
5. **Процедура вместо каталога** — как в Этапе 7 для обновлений Windows.
   Файлы прошивок привязаны к конкретной модели и ревизии, универсального
   набора не существует.
6. **Носитель FAT32 для M-FLASH обязателен.** Наша флешка для этого не
   годится ни одним разделом.

## 9. Рекомендации

1. **Каталог `tools/firmware/` строить по подкатегориям каналов, а не по
   вендорам**: `bios/` (процедура M-FLASH + бэкап SPI), `storage/`
   (`nvme-cli` + процедура получения бинарника), `peripheral/` (`fwupd` как
   инвентаризатор). Ни утилит, ни файлов прошивок не хранить — только
   процедуры, как в Этапе 7.
2. **Роутеры исключить** из группы (см. §7).
3. **Категорию `ISO/firmware/` не создавать** — FreeDOS-сборки с вендорскими
   утилитами для целевой станции не нужны, а DOS-путь обновления устарел.
   Убрать её из перечня зарезервированных категорий в `ventoy-partition/ISO/`.
4. **Intel FPT — только как средство восстановления**, не как штатный способ.
   И только если будет принято решение по его лицензии.
