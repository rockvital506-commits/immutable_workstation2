## 2. Новые находки

### N1. Файл ответа обязан содержать проход `windowsPE`

Ventoy раскладывает шаблон как `X:\autounattend.xml`. Setup кэширует файл
ответа только если он имеет валидное имя, лежит в допустимом пути поиска **и
содержит валидные настройки для текущего прохода установки**. Файл без секции
`windowsPE` не кэшируется — установка уходит в ручной режим, а Ventoy при этом
не сообщает об ошибке.

Подтверждено разбором реального случая (forums.ventoy.net, tid=2172): файл,
работавший в Rufus под именем `unattend.xml`, не сработал через Ventoy именно
из-за отсутствия прохода `windowsPE`.

**[вывод]** Каждый наш шаблон обязан содержать `<settings pass="windowsPE">` с
`SetupUILanguage`, `DiskConfiguration` и `ImageInstall`. Проверять наличие
прохода тестом, а не на глаз.

### N2. Встроенные переменные Ventoy: защита от установки на флешку

Формат — `$$VT_XXX$$`, файл обязан быть в UTF-8. Раскрытие не изменяет файл на
флешке. Для встроенных переменных Ventoy не спрашивает значение, а подставляет
сам.

| Переменная | Значение для нас |
|------------|------------------|
| `$$VT_WINDOWS_DISK_1ST_NONVTOY$$` | Первый диск, не являющийся Ventoy. Прямая защита от установки на флешку |
| `$$VT_WINDOWS_DISK_NONVTOY_CLOSEST_256$$` | Не-Ventoy диск, ближайший к 256 ГБ. Для MSI B12M это NVMe 256 ГБ — точное попадание |
| `$$VT_WINDOWS_DISK_MAX_SIZE$$` | Наибольший диск. Опасно при подключённом внешнем носителе |

Сама документация Ventoy формулирует риск прямо: жёстко заданный `DISK0`
«может установить ОС на неверный диск или даже на диск, где расположен Ventoy».

**[вывод]** В шаблоне не должно быть литерального `<DiskID>0</DiskID>`. Только
переменная. Для станции — `CLOSEST_256`, для универсального шаблона —
`1ST_NONVTOY`.

### N3. `autounattend.xml` в корне флешки применяется всегда

Дефект Ventoy 1.1.05 (issue #3168): если файл ответа лежит в корневом каталоге,
он применяется ко всем ISO и отказаться от него нельзя — даже при пустом
`auto_install`. Лечится только размещением файла в отдельном каталоге.

**[вывод]** Наш выбор `/ventoy/autoinstall/` вместо корня — не стиль, а
требование. Правило стоит зафиксировать в README каталога и в тесте.

### N4. Конфликт источников файла ответа

Если другой инструмент (Rufus, Ventoy) уже положил свой `autounattend.xml`
внутрь файлов установки Windows, этот файл выше в порядке поиска и получает
приоритет — наш шаблон молча игнорируется. Формулировка автора генератора
Schneegans: основная причина «не сработавшего» файла ответа — чужой
`autounattend.xml`, вставленный другим ПО.

**[вывод]** Диагностика «шаблон не применился» начинается с проверки
`C:\Windows\Panther\unattend.xml` и журналов в `C:\Windows\Panther\`, а не с
правки шаблона.

### N5. Семантика `timeout` и `autosel` — правило в README неполное

По официальной документации:

- `timeout` > 0 — меню появляется и по истечении выбирается пункт;
- `timeout` = 0 — меню появляется и ждёт выбора вечно;
- `timeout` **не задан** и `autosel` задан — меню **не появляется вовсе**,
  шаблон применяется сразу;
- `timeout` не задан и `autosel` не задан — то же, что `timeout` = 0.

Наше правило «не задавать timeout» верно, но неполно: при `autosel` шаблон
уходит в применение без спроса. Сейчас в `ventoy.json` ни `autosel`, ни
`timeout` нет — это и есть режим «ждать выбора», который нам нужен.

**[вывод]** Правило уточнить: **не задавать ни `timeout`, ни `autosel`**.
Занести в README и в тест, проверяющий `ventoy.json`.

### N6. Для 24H2 генератор работает, но встраивание скриптов в XML — нет

Автор генератора подтверждает: сгенерированные файлы работают с любой Windows
10/11, включая 24H2, в обоих режимах установки. Но для 24H2 установщик вызывает
`SetupPrep.exe`, и этот поток несовместим со встраиванием скриптов и файлов
внутрь `autounattend.xml`.

**[вывод]** `FirstLogonCommands`/`RunSynchronousCommand` — можно. Вложение
файлов в XML — нельзя, всё отдельными файлами на флешке.

### N7. Ключи обхода требований — состав и способ внесения

`HKLM\SYSTEM\Setup\LabConfig`, вносятся в проходе `windowsPE` через
`RunSynchronousCommand`:

| Значение | Что обходит |
|----------|-------------|
| `BypassTPMCheck` | TPM 2.0 |
| `BypassSecureBootCheck` | Secure Boot |
| `BypassRAMCheck` | 4 ГБ ОЗУ |
| `BypassStorageCheck` | свободное место |
| `BypassCPUCheck` | модель процессора |

Для целевой станции (MSI Modern 15 B12M-211RU, i3-1215U, 8 ГБ, TPM 2.0 есть)
обход **не требуется**. Он нужен универсальному шаблону под «зоопарк» железа.

### N8. `OOBE\BYPASSNRO` больше не работает

По состоянию на 2026-08 метод «Shift+F10 → `OOBE\BYPASSNRO`» заблокирован при
вводе одной строкой; `start ms-cxh:localonly` также больше не работает
надёжно. Локальная учётная запись создаётся через `UserAccounts/LocalAccounts`
в файле ответа, а не через команду в OOBE.

### N9. Локальная учётная запись требует отключённой сети

Для предложения локальной учётной записи сеть должна быть физически
отключена. Шаг 3 алгоритма («физическое отключение сети») это уже
обеспечивает — совпадение не случайное, его стоит назвать явно в процедуре.

### N11. persistence: подтверждение и ограничение

- Метка для Linux Mint — **`casper-rw`** (подтверждено официальной
  документацией и практикой).
- Создание: `sudo bash CreatePersistentImg.sh -s 16384 -t ext4 -l casper-rw`;
  по умолчанию размер 1 ГБ, ФС ext4.
- **Файл обязан лежать на первом разделе** Ventoy. Наш первый раздел exFAT —
  подходит. После копирования обязателен `sync`.
- Расширение без потери данных возможно **только для ext4**; XFS не
  поддерживается, потому что его нельзя неразрушающе уменьшить. Наш выбор
  ext4 согласован с этим.
- Официально протестированный образ в документации — `linuxmint-19.3`. Для
  22.3 это не проверено. Поддержка персистентности определяется **сборкой
  ISO**, а не Ventoy (это уже A6).

### N12. Имя файла бэкенда

`CreatePersistentImg.sh` создаёт `persistence.dat` по умолчанию, а не
`persistence.img`. В `ventoy.json` должно стоять то имя, которое реально
лежит на флешке. Практика: расхождение имени — частая причина «persistence не
работает».
