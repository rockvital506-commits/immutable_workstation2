# 08. Векторы атаки на применённые настройки

Дата исследования: 2026-10-07, сверка с первоисточниками 2026-10-10.
Контекст: Windows 11 IoT Enterprise LTSC 2024
на станции MSI Modern 15 B12M-211RU. Цель — понять, что именно отменяет наши
правки после того, как они применены, и чем это закрывать.

Документ дополняет `07-blocking-mechanisms.md`: там — чем блокировать,
здесь — что блокирует нас в ответ.

---

## A. Векторы атаки

### A1. Windows Update — основной канал

Подтверждено несколькими независимыми источниками: обновления Windows
возвращают системные настройки к значениям по умолчанию. Конкретные примеры из
обсуждения Microsoft TechCommunity: параметры Prefetch/SuperFetch и масштаб
текста для заданного разрешения откатываются после обновления. Прямого
способа запретить откат нет — только заранее сохранять значения и
восстанавливать после.

Что именно приходит через WU:

| Что | Эффект |
|-----|--------|
| Качественные обновления | Переписывают системные файлы, возвращают часть параметров |
| Драйверы | Заменяют выставленные вручную драйверы, ломают настройку устройств |
| Функциональные обновления | Фактически переустановка: наши правки не выживают |
| Пакеты приложений | Предустановленные appx возвращаются |
| Компонентные обновления | Приносят новые службы и задачи телеметрии |

**Вывод:** WU — главный вектор, но полное его отключение делает систему
уязвимее, чем система с телеметрией. См. рекомендацию R3.

### A2. Удаление `Registry.pol` — снимает все локальные политики одной командой

Самый опасный вектор для сценария «закрепить через GPO». Достаточно прав
локального администратора:

```powershell
Stop-Service wuauserv -Force
Remove-Item "C:\Windows\System32\GroupPolicyUsers" -Recurse -Force
Remove-Item "C:\Windows\System32\GroupPolicy" -Recurse -Force
Remove-Item "HKLM:\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate" -Recurse -Force
Start-Service wuauserv
```

Это штатный способ сброса локальных политик, он documented и широко известен.
Важная особенность: **удаление политики не откатывает «татуированные» значения**
(tattooing) — часть параметров остаётся в реестре, часть возвращается к
умолчанию. То есть результат непредсказуем.

Отдельно: `Registry.pol` лежит в `C:\Windows\System32\GroupPolicy\Machine\`
даже на машине без домена, и его можно править напрямую — например, модулем
`PolicyFileEditor` (`Set-PolicyFileEntry`) или утилитой LGPO. После правки
достаточно `gpupdate /force`, и значения возвращаются. Это же техника
закрепления исключений Defender, которую используют атакующие.

**Вывод:** закрепление через GPO без защиты самого `Registry.pol` — это
закрепление до первого администратора. См. рекомендацию R2.

### A3. Прямая правка ветки `Policies`

Значения политик физически лежат в `HKLM\SOFTWARE\Policies\...` и
`HKCU\SOFTWARE\Policies\...`. Их можно удалить `reg delete` без всякого
`gpedit`. Известный приём обхода: снять наследуемые права на ключе через
редактор безопасности и запретить доступ — тогда политика перестанет
применяться даже для локального администратора.

Обратная сторона: тот же приём работает против нас. Если мы закроем доступ к
ключу, а потом понадобится изменить политику, придётся сначала возвращать
права.

### A4. Планировщик задач

Задачи в ветках `\Microsoft\Windows\Application Experience\`,
`\Microsoft\Windows\Customer Experience Improvement Program\` и подобных
возвращают телеметрию. Задачи обновления в `\Microsoft\Windows\WindowsUpdate\`
и `\Microsoft\Windows\UpdateOrchestrator\` возвращают WU-поведение.

Отключённая задача может быть включена: обновлением, другой задачей,
приложением вендора или пользователем.

### A5. Службы

`DiagTrack`, `dmwappushservice`, `WSearch`, `SysMain` и прочие. Служба в
состоянии `Disabled` может быть возвращена в `Manual`/`Automatic`:
обновлением, установщиком, «оптимизатором».

Отдельно — служба `Update Orchestrator Service` (UsoSvc): у неё настроено
самовосстановление, и простое отключение часто не держится.

### A6. Магазин и предустановленные приложения

Предустановленные appx возвращаются после обновлений. Причина — снятие пакета
только для текущего пользователя (`Remove-AppxPackage`) без снятия
provisioned-пакета. Нужны **оба** действия:
`DISM /Remove-ProvisionedAppxPackage` и `Remove-AppxPackage`.

Обратный риск — не снятие, а **наличие** пакета, который установлен
пользователю, но не provisioned для всех: `sysprep /generalize` требует, чтобы
все приложения были provisioned. Официальное сообщение в журнале Sysprep
(`%WINDIR%\System32\Sysprep\Panther`): `... was installed for a user, but not
provisioned for all users. This package will not function properly in the
sysprep image.` Код `0x80073cf2`, который встречался в сторонних источниках, с
первоисточником не сверен.

### A7. Профиль пользователя

Обновления сбрасывают настройки локальных учётных записей: ярлыки рабочего
стола, панель задач, обои. Причина — Windows при обновлении иногда входит во
временный профиль. Диагностика: в
`HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList` появляются
дубли SID с суффиксами `.bak` / `.tmp`.

### A8. Драйверы из Windows Update

WU ставит драйверы автоматически и может **понизить** версию, заменив
свежий драйвер вендора на старый WHQL. Задокументированный случай: WU
откатывает драйвер Intel Xe на более старый.

Каналы отключения:

| Метод | Ключ / путь | Статус проверки |
|-------|-------------|-----------------|
| GPO «Do not include drivers with Windows Updates» | `Computer Configuration → Administrative Templates → Windows Components → Windows Update → Manage updates offered from Windows Update` | **Подтверждено** Policy CSP — Update |
| Реестр, политика | `HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate` → `ExcludeWUDriversInQualityUpdate = 1` | **Подтверждено** Policy CSP — Update: редакции Pro, Enterprise, Education, **IoT Enterprise / IoT Enterprise LTSC**; Windows 10 1607 и новее; ADMX `WindowsUpdate.admx` |
| Реестр, поиск при подключении устройства | `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\DriverSearching` → `SearchOrderConfig = 0` | **Ключ сообщества**, не документирован Microsoft. В источниках расхождение: встречаются значения 0, 1 и 3 |
| Реестр, состояние политики | `HKLM\SOFTWARE\Microsoft\WindowsUpdate\UpdatePolicy\PolicyState` → `ExcludeWUDrivers = 1` | **Ключ состояния**, а не политики. Система может переписать его сама |
| Реестр, поиск драйверов | `HKLM\SOFTWARE\Policies\Microsoft\Windows\DriverSearching` → `DontSearchWindowsUpdate = 1`, `DontPromptForWindowsUpdate = 1`, `DriverUpdateWizardWuSearchEnabled = 0` | **Проверено по коду** WinUtil 26.10.07, режим `Updates → security` |
| Реестр, метаданные устройств | `HKLM\SOFTWARE\Policies\Microsoft\Windows\Device Metadata` → `PreventDeviceMetadataFromNetwork = 1` | **Проверено по коду** WinUtil 26.10.07 |
| Точечно по устройству | `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\DeviceSetup\Settings` → `PreventDeviceDriverUpdate = 1` | Не сверено с первоисточником |
| Скрыть конкретное обновление | `wushowhide.diagcab` (Show or Hide Updates) | Упоминается Microsoft Q&A, с официальной страницы не сверено |

Опыт сообщества: надёжнее всего работает комбинация политики и ключей
`SearchOrderConfig` / `ExcludeWUDrivers`, а для конфликтного устройства —
блокировка по Hardware ID. Одной политики `ExcludeWUDriversInQualityUpdate`
бывает недостаточно, хотя именно она единственная документирована.

Из Policy CSP — Update также следуют механизмы, нужные для сужения канала:
`TargetReleaseVersion`, `ProductVersion`, `PauseFeatureUpdates`,
`PauseQualityUpdates`, `PauseFeatureUpdatesStartTime`,
`PauseQualityUpdatesStartTime`, `ManagePreviewBuilds`. Имена параметров
реестра для них с официальной страницей групповых политик **не сверены**.

**Важно:** отключение драйверов из WU не отключает обновления безопасности —
это разные классы обновлений.

### A9. Утилиты вендора

MSI Center и подобные возвращают свои службы, задачи и настройки, а заодно
тянут телеметрию. На LTSC их не будет по умолчанию, но они могут приехать с
драйверами с сайта производителя.

### A10. Сетевые каналы

Даже при `AllowTelemetry = 0` часть компонентов пытается ходить в сеть.
Закрывается на уровне hosts, межсетевого экрана и блокировкой доменов
телеметрии на маршрутизаторе.

### A11. Офлайн-доступ к носителю

Загрузка с внешнего носителя даёт полный доступ к кустам реестра и к
`Registry.pol` в обход любых ACL. Единственная защита — BitLocker и пароль на
BIOS/UEFI.

### A12. Smart App Control и изоляция ядра

На Windows 11 24H2 часть твиков сторонних утилит конфликтует со Smart App
Control и Memory Integrity. Проявляется не сразу и диагностируется трудно.

## C. Разбор предложенного сценария

Исходная гипотеза: **audit mode → закрепление через GPO → блокировка WU**.

**Итог согласования с заказчиком, 2026-10-07.** Из трёх пунктов гипотезы принят
один: закрепление через локальные групповые политики — вместе с защитой самого
носителя политики (R2). Audit mode отклонён как избыточный для одной станции
(R1). Блокировка Windows Update заменена сужением канала с временной паузой на
период обкатки настроек (R3). Связка инструментов утверждена по R4:
Win11Debloat → WinUtil → Sophia Script точечно → свои скрипты; GTweak в состав
не входит.

### C1. Audit mode — для этой задачи избыточен

Audit mode нужен для создания **эталонного образа** под тираж:
`Ctrl+Shift+F3` на экране OOBE, настройка под встроенным администратором,
затем `sysprep /generalize /oobe` и снятие образа.

Цена, которую он добавляет при работе с одной станцией:

| Ограничение | Следствие | Источник |
|-------------|-----------|----------|
| **Не предназначен для тестирования и валидации** | Проверять работу ОС можно только после завершения OOBE — а наш сценарий «настроить и проверить» упирается ровно в это | `learn.microsoft.com`, Audit mode overview |
| Настройки прохода `oobeSystem` не применяются | Часть файла ответов в audit mode просто не отработает | там же |
| Вход под встроенным администратором, который сразу отключается | Заставка с паролем может заблокировать вход обратно | там же |
| Установка и обновление приложений из Store ломает `sysprep` | Приложение, «установленное для пользователя, но не подготовленное для всех», не работает в образе | `learn.microsoft.com`, Sysprep (Generalize) |
| `CopyProfile` — legacy, не рекомендован | Часть настроек не переносится | `learn.microsoft.com` |
| Настройки Default Apps шифруются хэшем пользователя | `CopyProfile` их не переносит, Windows сбрасывает их при первом входе | там же |
| `CopyProfile` работает только если нет других профилей | Любая учётка, созданная установщиком, ломает механизм | там же |

При этом наша схема уже обходит OOBE через `autounattend.xml` — то есть
главную выгоду audit mode мы получаем без него.

### C1a. Две правки этого раздела, 2026-10-10

Проверка по официальным страницам `learn.microsoft.com` показала, что две
записи выше были неверны.

**Первое — лимит запусков sysprep.** Было записано «порядка четырёх
перезапусков, дальше нужен `/skiprearm`». На самом деле по таблице Microsoft
лимит — **1001 запуск** для Windows 8.1, Server 2012 и новее, то есть и для
Windows 11. Лимит «3 запуска» относится к Windows 7, Server 2008 R2 и
Server 2008. Там же указано, что `SkipRearm` имел смысл в прежних версиях, а
при ключа корпоративного лицензирования или розничном ключе Windows
активируется автоматически.

**Второе — направление проблемы с приложениями.** Было записано, что sysprep
ломает «снятие appx, установленного, но не provisioned». Официальная
формулировка обратная: `sysprep /generalize` требует, чтобы все приложения
были provisioned для всех пользователей, а ошибка возникает, когда приложение
**установлено для пользователя, но не подготовлено для всех** — типичное следствие
установки или обновления из Store. Сообщение в журнале:
`... was installed for a user, but not provisioned for all users`. То есть
риск создаёт добавление приложений из Store, а не их снятие.

Обе правки усиливают, а не ослабляют вывод C1: audit mode для одной станции
не нужен, а для проверки настроек Microsoft прямо рекомендует другую среду.

Профиль по умолчанию настраивается надёжнее без `CopyProfile`, прямой правкой
куста:

```cmd
reg load HKU\Default C:\Users\Default\NTUSER.DAT
reg add "HKU\Default\..." /v ... /t REG_DWORD /d ... /f
reg unload HKU\Default
```

**Вывод:** audit mode оправдан, только если планируется тиражирование образа
на несколько одинаковых станций. Для одной MSI B12M — лишнее звено.

### C2. Закрепление через GPO — верно, но недостаточно

GPO действительно правильный слой: значения политик переживают перезагрузку,
видны в `gpresult`, и это штатный механизм Microsoft. Но вектор A2 снимает
всё одной командой при наличии прав администратора.

Закрепление становится реальным только вместе с защитой носителя политики:
ACL Deny на `C:\Windows\System32\GroupPolicy` и на ключевые ветки
`HKLM\SOFTWARE\Policies`. Это механизм M6 из `07-blocking-mechanisms.md`.

Цена: при необходимости изменить политику придётся сначала возвращать права.
Нужен документированный способ отката, иначе станция станет
необслуживаемой.

### C3. Блокировка WU — верно направление, неверна мера

Полное отключение Windows Update:
- лишает станцию обновлений безопасности;
- на части редакций ломается вместе с `AllowTelemetry = 0`;
- у нас же в требованиях записано: **пост-тест Центра обновления обязателен**.

Правильная мера — не отключить, а **сузить канал**: оставить обновления
безопасности, закрыть драйверы, функциональные обновления, потребительские
компоненты и автоустановку из Store. Это закрывает A1 и A8, не создавая дыры.

## D. Рекомендации

### R1. Не использовать audit mode для одной станции

Работать по существующей схеме: установка через `autounattend.xml` при
отключённой сети → драйверы → настройки. Audit mode включить в план только
если появится задача тиражирования.

### R2. Закреплять GPO вместе с защитой носителя политики

Порядок: применить политики → проверить `gpresult /h` → выставить ACL Deny на
`C:\Windows\System32\GroupPolicy` и на ветки `HKLM\SOFTWARE\Policies\...` →
задокументировать способ снятия прав. Без последнего шага станцию потом не
обслужить.

### R3. Не отключать Windows Update, а сузить его канал

Оставить обновления безопасности. Закрыть:
- драйверы — `ExcludeWUDriversInQualityUpdate = 1` + `SearchOrderConfig = 0` +
  `ExcludeWUDrivers = 1` в `PolicyState`;
- функциональные обновления — закрепление целевой версии (TargetReleaseVersion);
- потребительские компоненты — `DisableWindowsConsumerFeatures`;
- автоустановку из Store.

### R4. Инструменты применять последовательно, а не вместе

Win11Debloat и WinUtil частично пересекаются по правкам. Применение обоих
сразу даёт непредсказуемый результат и два набора откатов.

Предлагаемая связка:
1. **Win11Debloat 2026.08.24** — основной слой: реестр и GPO, есть бэкап,
   откат и `-WhatIf`. Прогнать сначала с `-WhatIf`.
2. **WinUtil** — как watchdog: его обнаружение отката твиков закрывает M9, и
   это уже готовая реализация, писать свою избыточно.
3. **Sophia Script, пакет для LTSC 2024** — точечно, для функций, которых нет
   в первых двух. Закрепить конкретную версию.
4. **Свои скрипты** — только то, чего нет ни в одном инструменте: блокировки
   по `research/06-services-blocklist.md` и `07-blocking-mechanisms.md`,
   ACL-закрепление политик, пост-проверка.

GTweak не рекомендовать до проверки лицензии, наличия отката и поддержки LTSC.

### R5. Каждое действие — с бэкапом реестра и способом отката

Не «общая точка восстановления», а выгруженный `.reg` по каждой группе
правок. Точка восстановления не переживает переустановку и не помогает, если
сломалась загрузка.

### R6. Пост-проверка после перезагрузки обязательна

Часть механизмов самовосстановления возвращает значения только после
перезагрузки или по расписанию. Проверять надо минимум дважды: сразу после
применения и после перезагрузки. Это уже пункт 11 в `algorithm.md` станции.
