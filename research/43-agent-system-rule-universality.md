# Универсальность правил: отбор, смысл и проверка результата

## 1. Решение владельца и изменение курса

Владелец уточнил приоритет: **чем выше универсальность правила, тем важнее
сохранить его смысл; менее универсальное передаётся на уровне общих смыслов;
неуниверсальное игнорируется** при формировании переносимых правил.

Это не требование копировать все source bytes. Начатое направление
[42](42-agent-system-lossless-rule-adapter.md) не применяется как основной
адаптер: оно решало сохранность представления, а не градуированный отбор смысла.
Lossless допустим лишь как вспомогательная проверка immutable source/basis.
Прерванный experimental code не зарегистрирован/не введён. Результат его tests
неизвестен; никакого PASS/готовности не выводим из прерванной команды.

Здесь зафиксирована корректировка design, **не реализованный semantic classifier**,
не новая normative revision/core, не permission выпуска/экспорта/активации.
Действующие immutable версии не редактируются. Baseline — cadf600, registry
19entities/31revisions/111norm/31approvals/142refs, без изменений.

## 2. Единица анализа — смысл, не файл

Один файл/абзац может смешивать универсальное правило, частный механизм и пример.
Классификация целого файла как universal/non-universal теряет различия. Разбирать
на связанные смысловые единицы с exact source path/revision/hash/locator:

- обязанность/запрет/допустимое действие;
- условие применимости, исключение, предел полномочия;
- зависимости, определяющие смысл, и уровень проверки;
- конкретный механизм/пример/частное решение как отдельные данные.

Источник и его роль сохраняются для traceability, но не автоматически становятся
переносимым правилом. Нельзя сделать универсальной частную инструкцию только
удалением имени продукта или пути. Нельзя отдельно обобщить запрет и отбросить
его исключение либо условие: рассматривать связанную группу целиком.

## 3. Три маршрута и неизвестное

| Универсальность | Передача | Обязательная проверка |
|---|---|---|
| Высокая | Сохранить нормативный смысл: обязательства, запреты, условия, исключения, область/зависимости/границы полномочий | Не потеряно/не ослаблено исходное требование; не добавлено новое полномочие/запрет; иная формулировка допустима только при проверенной эквивалентности |
| Ограниченная, есть обоснованный общий смысл | Передать применимый общий принцип; привязанные инструменты/пути/платформы/частные параметры не выдавать за universal obligation | Обобщение действительно следует из source, не расширяет требование сверх основания и не переносит приватный случай; обозначены пределы применимости |
| Неуниверсальная | Исключить из переносимых правил; не тащить частные операции/архитектуру/параметры как общие требования | Нет случайного включения или скрытого наследования; исходник/история не удалены |
| Неопределённая/смешанная/спорная | Не назначать уверенный класс автоматически; выделить связанные единицы и показать вопрос/основание | Unknown не считается ни согласованным universal rule, ни безопасно отброшенным mandatory meaning |

Классификация должна иметь обоснование, не только label/числовой score. Приоритет
review растёт с универсальностью и последствиями искажения. Более низкая
универсальность **не разрешает произвольный пересказ**: сохраняется доказуемый
общий смысл, а не привлекательная новая рекомендация от адаптера.

«Игнорировать» означает не включать в переносимые правила. Это не команда
удалить source/history, обойти относящийся запрет или проигнорировать реальную
частную задачу владельца в её исходной области. Обязательное ядро не ослабляется
под видом переклассификации: изменение его требований требует отдельного решения.
Действительные ограничения/отзывы применяются к связанным сущностям независимо
от того, переносится ли их private source text; они не снимаются классификатором.

## 4. Проверка семантического результата — центральный контракт

Для каждой исходной единицы: source reference → обоснованная классификация →
маршрут preserve/generalize/exclude → результирующее правило либо причина
исключения → относящиеся проверки/unknown. Связанные условия/исключения/зависимости
явно прослеживаются. Это working trace, не второй нормативный источник/registry.

Проверять в обе стороны:

1. **Полнота:** все высокоуниверсальные обязательные смыслы и связанные оговорки
   представлены; нельзя молча отбросить неудобный запрет/ограничение/неизвестное.
2. **Отсутствие привнесённого:** итог не добавляет неутверждённых обязанностей,
   приоритетов, разрешений или универсальных утверждений из частного примера.
3. **Корректность обобщения:** общий смысл менее универсальной единицы обоснован,
   private detail отделён, applicability не расширена без основания.
4. **Исключение частного:** non-universal данные не попали в правила через prompt,
   metadata, примеры, defaults, transitive dependencies или hidden fallback.
5. **Сам результат:** проверять фактически полученные texts/structure/roles, не
   только намерение producer/self-report/hash его собственного output.
6. **Применение:** отдельно проверить visibility/precedence/scopes/conflicts/
   context limits/behavior в согласованной среде. Semantic text review и byte
   integrity не доказывают автоматически корректное исполнение агентом.

Пока нет применимой semantic проверки, нельзя автоматически считать иной текст
эквивалентным. Сохранение source без изменений может быть безопасным fallback
для высокоуниверсальной единицы **в её области**, но не повод копировать частные
сущности и не разрешение применять её в неподходящем context. При неустранимой
неопределённости затронутый перенос блокируется/вопрос предъявляется владельцу.

## 5. Примеры различения (иллюстрации, не новые правила)

- «Не объявлять действие успешным без проверки результата»: высокий общий смысл;
  не заменить на более слабое «желательно проверить».
- Частная команда сравнения checksum конкретного файла: если source обосновывает
  общий принцип целостности, передать этот принцип, а не обязательность этой
  команды/пути/ОС для любой среды. Самостоятельно новую обязанность не выдумывать.
- Конкретная схема разделов/модель устройства/проектный каталог: в универсальные
  правила не переносить. Её присутствие в истории не делает её универсальной.
- «Запрет, кроме явно определённого условия»: условие — часть смысла. Ни убрать
  исключение (усиление), ни превратить его в общий обход (ослабление) нельзя.

## 6. Следующая разработка и доказательная граница

До новой implementation зафиксировать reviewable unit-level trace на реально
относящихся универсальных сущностях, с linked exceptions/dependencies и adversarial
cases (ослабление, усиление, чрезмерное обобщение, private leakage, missing condition).
Квалифицировать preservation/generalization/exclusion отдельно, а не продвигать
lossless контейнер как решение semantics. Учитывать результат фактической проверки
и его уровень; не приравнивать agent self-review к independent owner review.

Этот checkpoint меняет критерии дальнейшей работы, не объявляет semantic transfer
реализованным. Старые profiles/consumers/history не переключаются, actual
release/export/activation/new target environment не разрешаются.
