# alternative_algorithm.md — альтернативные варианты шагов


**Цель алгоритма:** дать содержательно отличающиеся маршруты достижения целей
основного алгоритма с явными условиями выбора и ограничениями.

**Критерии успеха:** каждый проработанный вариант достигает цели своего шага;
отличия и ограничения описаны; практическая проверка отделена от проектирования.

**Навигация:** [Шаг 1 — только WinPE](#msi-alt-diag-01) ·
[варианты установки](#3-альтернативные-варианты) ·
[непроверенное](#5-не-проверено-на-месте) · [журнал практики](field-notes.md).
Остальные элементы приводятся к §7.5 поэтапно при их проработке.

Альтернативные варианты шагов алгоритма станции MSI Modern 15 B12M-211RU.
Правило — [`CONVENTIONS.md`](../../../CONVENTIONS.md) §7.4. Рекомендуемый
вариант каждого шага живёт в
[`algorithm.md`](algorithm.md); этот файл его не заменяет и вместо него не

## 1. Как читать этот файл

Файл покрывает Шаг 1 и три шага установочного блока. Это пилотная проверка правила
§7.4: ретрофит остальных двенадцати шагов — отдельная задача, решение о нём
принимается после того, как пилот покажет себя на реальном железе.

**Историческое решение владельца 2026-10-21: затвор в силе.** Ретрофит двенадцати шагов
отложен до выезда. Проверить пилот на железе из рабочей среды нечем —
очередь B не исполняется без носителя, Windows и сети вне белого списка,
поэтому условие затвора не выполнено и снимать его решением не стали.
Когда ретрофит начнётся, шаг подтверждения — по одному шагу: шаг, вывод
результатов и запрос на подтверждение, коммит, следующий шаг. Заново
спрашивать о затворе не нужно: вопрос закрыт до выезда, а не снят.

**Отбор альтернативы.** Запись появляется только при обоих условиях §7.4.3:
цели шага достигаются полностью и подход имеет другую природу либо результат
имеет другие характеристики. Второй экземпляр того же механизма
альтернативой не считается.

По этой причине в файле нет записей для шагов, где запасной путь отличается
только интерфейсом. Конкретно: разметка диска через `MiniTool Partition
Wizard` или `DiskGenius` из сборки Стрельца альтернативой шагу 5 не является —
это тот же императивный механизм правки таблицы разделов, только с графическим
интерфейсом вместо командной строки. Природа подхода и характеристики
результата не меняются.

**Два обязательных исследования.** Обе части §7.4.1 выполнены по
[`tools/diagnostics/strelec-tools.md`](../../../tools/diagnostics/strelec-tools.md)
и по веб-источникам. Ограничение веб-части зафиксировано в разделе 5: часть
первоисточников из рабочей среды недоступна, и утверждения, опирающиеся
только на них, помечены как непроверенные.

Практика началась 2026-10-22. Владелец разрешил поэтапную проработку:
Шаг 1 оформлен 2026-10-23; это не снимает затвор для остальных шагов
и не подтверждает установочные варианты практикой.

## 3. Альтернативные варианты

<a id="msi-alt-diag-01"></a>
### Шаг 1. Бережная диагностика полностью в Strelec

**Цель шага.** Получить достаточную аппаратную картину без зависимости от
работоспособности и пользовательской сессии установленной Windows.

**Критерии успеха:** оборудование и диски идентифицированы; схема разделов,
SMART и температуры получены либо недоступность явно записана; заключение
содержит ограничения; результаты сохранены вне RAM-диска. Полная проверка
исправности всех компонентов не является достижимым обещанием этого шага.

**Рекомендуемый вариант.** Фактически выполненный смешанный маршрут
[основного Шага 1](algorithm.md#msi-diag-01): исходные сведения и отчёт SMART
из живой Windows, аппаратные наблюдения в Strelec. Живая ОС не обязательна
для чтения SMART или разделов; её использование само по себе не преимущество.

**Альтернативный вариант.** Уровень 1 цепочки §7.4: от загрузки до сохранения
результатов используется только имеющийся Strelec WinPE11 x64. Установленная
Windows не запускается. Другие утилиты не скачиваются.

**Средства альтернативы.**

| Средство | Тип | Путь на флешке |
|---|---|---|
| DiskPart | средство среды | `SYSTEM:` |
| CrystalDiskInfo, HWiNFO, Hard Disk Sentinel | имеющиеся средства Strelec | `SYSTEM:` (загруженная WinPE) |
| [Полевой журнал](field-notes.md) | документация | `BUILD:/field-notes.md` |

**Чем отличается.** Независимая загрузочная среда вместо зависимости от
живой ОС в начале маршрута. Общие аппаратные операции не становятся другим
методом измерения: отличие — среда исполнения и доступность при незагрузке ОС.
Не создавать искусственную альтернативу скачиванием другого SMART-просмотрщика.

**Плюсы альтернативы.** Применима при незагружающейся Windows; единая среда,
меньше фоновой активности установленной ОС, меньше переключений оболочек.

**Минусы альтернативы.** Собственные драйверы и ограничения WinPE; датчики
могут быть недоступны. Не характеризует поведение установленной Windows.
Сохранение на рабочем столе WinPE не обеспечивает постоянной копии.

**Остановка и переход.** Общие ограничения и условия остановки
[MSI-DIAG-01](algorithm.md#msi-diag-01) обязательны: никаких тестов поверхности,
self-test, стрессов, исправлений и изменений разделов. При зависании, исчезновении
диска, ошибке ввода-вывода или критическом предупреждении остановиться и согласовать
продолжение. Дополнительное исследование не назначать автоматически.

**Инструкция.** Загрузить имеющийся Strelec в UEFI, WinPE11 x64. Для схемы
разделов, SMART и температур использовать общие одноразовые блоки
[MAP](algorithm.md#msi-diag-01-map), [SMART](algorithm.md#msi-diag-01-smart),
[IDLE](algorithm.md#msi-diag-01-idle) — не повторять уже выполненные проверки.
В варианте только WinPE выбрать постоянное место хранения по метке тома;
рабочие результаты сохранять туда, а не только на X:. Не предполагать буквы
из живой Windows. VTOYEFI не использовать и не изменять. Составить заключение
по [VERDICT](algorithm.md#msi-diag-01-verdict). Лицензии, SSH, браузеры,
пароли и прочие пользовательские данные сюда не входят.

**Достижение цели.** Маршрут покрывает цель аппаратной диагностики, но не
инвентаризацию состояния установленной ОС. В практике 2026-10-23 общие
аппаратные проверки выполнены в Strelec, результатов достаточно. Полный
автономный маршрут до сохранённого комплекта отчётов не подтверждён:
постоянное сохранение всех снимков и внешняя SHA256-сверка остаются открытыми.
Не обозначать маршрут полностью проверенным; текущие результаты использовать
по [журналу](field-notes.md), без повторной аппаратной диагностики.

### Шаг 5. Разметка NVMe

**Цель шага.** Получить чистую оптимальную разметку вместо заводской.

**Рекомендуемый вариант.** Уровень 1. `diskpart` в WinPE Стрельца: `clean`,
`convert gpt`, четыре раздела вручную по размерам из файла ответа. Императивная
правка таблицы разделов до начала установки.

**Альтернативный вариант.** Уровень 1. Разметку выполняет установщик Windows по
секции `DiskConfiguration` файла ответа
[`answer/autounattend-ltsc-2024.xml`](answer/autounattend-ltsc-2024.xml).
Отдельного шага разметки нет: `WillWipeDisk=true` очищает диск, четыре
`CreatePartition` создают ту же схему. Перехода на уровень ниже нет — средство
то же по классу, другое по механизму.

**Средства альтернативы.**

| Сущность | Тип | Путь на флешке |
|---|---|---|
| [`answer/autounattend-ltsc-2024.xml`](answer/autounattend-ltsc-2024.xml) | файл ответа | `BUILD:/answer/` |
| `setup.exe`, установщик Windows | средство ОС | `SYSTEM:` |

**Чем отличается.** Природа подхода другая: декларативное описание разметки,
которое применяет установщик, вместо императивной последовательности команд,
которую применяет оператор. Характеристика результата тоже другая — диск
выбирает не оператор номером, а установщик переменной
`$$VT_WINDOWS_DISK_NONVTOY_CLOSEST_256$$`.

**Плюсы альтернативы.**

- Устраняется риск, описанный в шаге 5 как критический: `clean` на диске 0,
  которым может оказаться флешка. Номер диска не задаётся вручную вовсе.
- Невозможно расхождение между разметкой шага 5 и разметкой файла ответа —
  источник схемы один. Именно это расхождение уже было найдено и исправлено в
  версии 1.3 алгоритма.
- На одну ручную операцию меньше в среде, где ошибка необратима.

**Минусы альтернативы.**

- Разметка не видна до установки. Проверить четыре раздела и выравнивание
  можно только после того, как система уже поставлена.
- `WillShowUI=OnError`: при ошибке установщик покажет интерфейс выбора диска,
  и дальше решение принимает оператор в стрессовой точке процесса.
- Требует, чтобы установщик увидел NVMe. Если контроллер в режиме VMD и
  драйвер не подсунут, установка остановится на выборе диска — тогда
  рекомендуемый вариант с его явной диагностикой предпочтительнее.
- Откат только образом из шага 2; промежуточного состояния «чистый диск с
  готовой разметкой» не существует.

**Достижение цели.** Критерий тот же, что в шаге 5: четыре раздела WinRE 500
МБ, System 260 МБ, MSR 128 МБ, Windows на остаток, выравнивание 4096. Проверяется
после установки через `diskpart` → `list volume` и
`Get-Partition | Select PartitionNumber, Offset, Size`. Равносилен критерию
рекомендуемого варианта: сравниваются те же четыре раздела и то же смещение.

**Не проверено.** Фактическое применение `DiskConfiguration` к NVMe за
контроллером Intel VMD на этом железе; поведение установщика при
`WillShowUI=OnError` на конкретном диске.

### Шаг 6. Установка LTSC

**Цель шага.** Поставить ОС без мусора и без походов через OOBE вручную.

**Рекомендуемый вариант.** Уровень 1. Загрузка ISO LTSC через Ventoy,
установщик Windows проходит specialize-проход по файлу ответа
[`answer/autounattend-ltsc-2024.xml`](answer/autounattend-ltsc-2024.xml).
Развёртывание выполняет `setup.exe`.

**Альтернативный вариант.** Уровень 1. Развёртывание образа средствами WinPE
Стрельца: `DISM /Apply-Image` из `install.wim` на подготовленный раздел, затем
`bcdboot` для загрузчика. Установщик Windows не запускается, specialize-проход
не проходим.

**Средства альтернативы.**

| Сущность | Тип | Путь на флешке |
|---|---|---|
| [`WinPE_11-10_Sergei_Strelec_x86_x64_RU.iso`](../../../ventoy-partition/ISO/winpe/) | образ | `VENTOY:/ISO/winpe/` |
| [`en-us_windows_11_iot_enterprise_ltsc_2024_x64_dvd_f6b14814.iso`](../../../ventoy-partition/ISO/windows/) | образ, источник `install.wim` | `VENTOY:/ISO/windows/` |
| `DISM`, `bcdboot` | средство ОС | `SYSTEM:` |

**Чем отличается.** Природа подхода другая: прямое развёртывание содержимого
образа на раздел вместо прохода через установщик с его specialize-проходом.
Состояние на выходе другое — система развёрнута, но не настроена: нет
сгенерированного SID-профиля машины, нет выполненного specialize, учётная
запись и имя компьютера задаются отдельно при первом входе или через
`unattend.xml` в `C:\Windows\Panther`.

**Плюсы альтернативы.**

- Не зависит от того, как установщик разбирает файл ответа. Развёртывание
  детерминировано: что в образе, то и на диске.
- Драйверы можно интегрировать в образ до применения, и система поднимается
  сразу с ними. Это закрывает проблему NVMe за VMD, которую рекомендуемый
  вариант решает обходом в BIOS.
- Полный контроль над каждым этапом; сбой локализуется конкретной командой, а
  не падением установщика на неопределённой фазе.
- Не нужен обход требований к железу: проверка TPM и Secure Boot живёт в
  установщике, а не в развёртывании образа.

**Минусы альтернативы.**

- Specialize-проход не выполняется. Часть настроек, которые в рекомендуемом
  варианте применяет установщик, придётся применять отдельно.
- Больше ручных операций в точке, где цена ошибки — переустановка.
- `bcdboot` нужно вызвать с верными ключами под UEFI; ошибка даёт
  незагружающуюся систему при корректно развёрнутом образе.
- Файл ответа в рекомендуемом варианте решает сразу несколько задач
  (разметка, ключ, учётная запись). Здесь их надо решать по отдельности.

**Достижение цели.** Цель — ОС без мусора и без ручного OOBE. Критерий
рекомендуемого варианта: система загружается, учётная запись создана,
телеметрия не ушла до шага 9. В альтернативе то же достигается, но проверка
дополняется: `dism /image:W:\ /Get-CurrentEdition` подтверждает редакцию IoT
Enterprise LTSC, `bcdedit /enum` — наличие загрузчика, первый вход проходит
без OOBE только если `unattend.xml` положен в `C:\Windows\Panther`. Без
последнего условие «без походов через OOBE вручную» не выполняется, и
альтернатива цель шага не достигает.

**Не проверено.** Состав `install.wim` этого ISO — количество индексов и
какой из них IoT Enterprise LTSC; поведение specialize при развёртывании
через `DISM /Apply-Image` на этом железе.

### Шаг 7. Драйверы

**Цель шага.** Завести всё железо из проверенных INF, без драйвер-паков.

**Рекомендуемый вариант.** Уровень 1. `DISM /Online /Add-Driver /Recurse` в
установленной ОС из каталога [`drivers/`](drivers/), заполненного на шаге 2.1.
Драйверы ставятся в работающую систему после установки.

**Альтернативный вариант.** Уровень 4. Офлайн-интеграция в образ до установки:
[`integrate-drivers.sh`](../../../tools/drivers/export/scripts/integrate-drivers.sh)
в режиме `--image` монтирует `install.wim` и добавляет драйверы в него.
Система устанавливается уже с драйверами.

Уровень 4, а не 1: средство здесь — наш скрипт (`type=script` в
`manifest.csv`), а не встроенная утилита WinPE. По §7.4.2 уровень 4
дополнительно требует прохождения §7.1. Оно пройдено: исследование
[`research/13-offline-updates.md`](../../../research/13-offline-updates.md),
вариант G1 «Только драйверы», `DISM /Add-Driver /Recurse` в образ или в
установленную систему.

**Средства альтернативы.**

| Сущность | Тип | Путь на флешке |
|---|---|---|
| [`integrate-drivers.sh`](../../../tools/drivers/export/scripts/integrate-drivers.sh) | скрипт | `TOOLS:/drivers/export/scripts/` |
| [`drivers/`](drivers/) | каталог INF | `BUILD:/drivers/` |
| `DISM` | средство ОС | `SYSTEM:` |

**Чем отличается.** Природа подхода другая: обслуживание образа
(offline servicing) вместо установки драйверов в работающую ОС (online
servicing). Состояние на выходе другое — драйверы присутствуют в
`install.wim` и попадают в каждую систему, развёрнутую из этого образа, а не
в одну уже установленную.

**Плюсы альтернативы.**

- Решает проблему, которую рекомендуемый вариант решить не может: установщик
  не видит NVMe за контроллером VMD, и установка останавливается до шага 7.
  Драйвер IRST/VMD в образе доступен установщику на фазе выбора диска.
- После установки сеть, звук и Bluetooth уже работают; шагов «поставить
  драйвер, чтобы скачать драйвер» нет.
- Проверка `--dry-run` есть в скрипте, состав добавляемого виден до правки
  образа.

**Минусы альтернативы.**

- Правится `install.wim` на носителе. Нужна копия исходного ISO, иначе
  эталонный образ потерян; это противоречит принципу неизменяемости носителя,
  из которого исходит репозиторий.
- Драйверы конкретной станции попадают в образ, общий для всех установок. Для
  одной станции это приемлемо, для переиспользования образа — нет.
- Интеграция в образ не отменяется `DISM /Online /Remove-Driver`; откат —
  восстановлением исходного образа.
- Требует DISM в среде, где он есть. Скрипт фиксирует это явно: режим
  `--image` доступен в Windows и WinPE, в Linux не поддерживается.

**Достижение цели.** Критерий тот же, что в шаге 7: `pnputil /enum-devices
/problem` возвращает 0 проблемных устройств, сетевой адаптер в состоянии Up.
Дополнительно проверяется, что драйверы действительно пришли из образа, а не
из Windows Update: `pnputil /enum-drivers` показывает опубликованные имена
`oem*.inf` из `drivers/`.

**Не проверено.** Фактическая интеграция в `install.wim` этого ISO;
совместимость каждого INF из `drivers/` с офлайн-обслуживанием — часть INF
рассчитана только на установку в работающую ОС.
