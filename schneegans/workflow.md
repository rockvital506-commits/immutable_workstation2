# Регламент взаимодействия — версия 1, согласован 2026-10-24

## 1. Входные сведения

До первого блока — **только паспорт станции, будущая ОС, назначение**.
Не выносить заранее в обязательное ТЗ разметку, сеть, учётные записи, политики,
набор компонентов, пределы автоматизации, ветви или окончательные цель/критерии.
Ранее согласованные решения остаются видимыми: учитывать их при соответствующем
блоке; конфликт показать владельцу, не отменять молча. Старый XML — свидетельство
прошлых решений, а не автоматически принятая спецификация нового кандидата.

## 2. Полнота рассмотрения

Сверить реестр с актуальной формой и версией генератора. Каждому блоку дать
стабильный ID; название и позиция могут измениться, ID не переиспользовать.
Отдельно учитывать импорт, пресеты и вывод формы. Не ставить «рассмотрено»
по одному ознакомлению с названием. Все поля, значения и условно открывающиеся
поля должны быть объяснены. Большие однородные справочники языков/часовых поясов
объяснять по смыслу и способу выбора; разные механизмы не объединять.

## 3. Цикл одного блока

1. Объяснить назначение, каждое поле и варианты, пустое значение/умолчание,
   интерактивность, последствия, механизм, ограничения и условия применимости.
2. Разобрать существенные для станции варианты и сценарное ветвление.
3. Дать рекомендацию, запросить решение. До ответа это не согласованная настройка.
4. Записать выбор и причины, отказ от альтернатив, связи, вопросы и проверку.
5. Если нужна реализация, сначала согласовать её необходимость. Затем отдельный
   подшаг: причина → цель/критерии → механизм → код/файл → интеграция → ошибки/
   журнал/остановка → проверки → подтверждение → результат.
6. Проверить связи с прошлыми и предстоящими блоками, алгоритмами и носителем.
7. Зафиксировать карточку и соответствующий подшаг алгоритма. До назначения
   номера шага хранить проекцию подшага в карточке, не перенумеровывать алгоритм
   самостоятельно. Не переоткрывать инвентаризационный Шаг 2 ради генератора.

Решения: явное значение / штатное поведение / интерактивно / дополнительный
механизм / вне XML / несколько сценариев / отложено с конкретной зависимостью.
«Не нужно» требует основания; не пропускать блок. Рекомендация ≠ выбор владельца.

## 4. Формирование целей и проверок

Окончательная цель и критерии успеха шага — **результат разбора**, не входной
фильтр опций. При каждом решении уточнять ожидаемое поведение и его проверку.
После связанных групп пересматривать формулировки; отмечать «формируется»,
«предварительно», «согласовано в ревизии», «требует пересмотра».
Перед практическим действием его собственные цель/критерии и остановка уже
должны быть определены. Если решение меняется, проверить влияние на общую цель.

## 5. Сквозные проверки

После блока — локальные связи; после группы — цепочка; перед генерацией —
вся спецификация; после генерации — фактический код, не только галочки.
Связи: образ/редакция/ключ/активация; диск/разметка/WinRE/шифрование;
пользователь/первый вход/скрипты/очистка; сеть/драйверы/OOBE/обновления;
удаление/административные клиенты/зависимости. У изменения должен быть понятный
владелец применения, чтобы XML, отдельный скрипт и ручной этап не отменяли друг друга.
Конфликт предъявлять с вариантами, возвращаться к затронутому решению.

## 6. Две генерации и сохранение

Когда все блоки разобраны, закрыть существенные вопросы либо пометить
эксперимент. Зафиксировать ревизию решений, ветвь, текущие цель/критерии, дату,
коммит генератора. Агент готовит свой кандидат до изучения XML сайта;
сайт формирует второй. Оба основаны на одной спецификации, поэтому совпадение
не доказывает правильность. Не имитировать результат сайта при его недоступности.
По [плану проверки](knowledge/validation.md) сравнить, обсудить, при необходимости
вернуться к блокам. Итог — не механическое слияние кандидатов.

Все сформированные/обсуждаемые версии сохранять в нумерованных ревизиях без
перезаписи. Оригинал сайта не править. Исправления — новая ревизия. Действующий
итог в `answer/` билда, история/ссылки в гайде. Секреты — вне Git; обезличенную
копию явно маркировать. Исходный приватный артефакт не называть побайтово равным
обезличенному. Принятие XML ≠ разрешение на форматирование.

## 7. Как агент работает с меняющимся гайдом

Перед продолжением прочитать регламент, контекст билда, реестр, решения и
зависимости, текущие цель/критерии, последнюю ревизию/проверки. Не опираться
только на память чата. Новый запрос владельца имеет приоритет и отражается
в документах после уточнения конфликтов.

Различать четыре слоя: факт о генераторе (источник/версия), общая рекомендация
(область применимости), решение билда (подтверждение), практика (среда/результат).
Новое знание: проверить источник → найти затронутые блоки/билды → отметить риск
или устаревание → согласовать изменение текущего билда → новая ревизия.
Не переписывать молча принятые старые билды. Исправлять ошибочную актуальную
информацию, сохраняя причину, прежний вывод и затронутые версии.
Лайфхак без границ применимости и проверки — наблюдение, не рекомендация.

Устойчивые знания переносить из ревизий в справочник, повторы заменять ссылками,
устаревшее помечать с заменой, противоречия не скрывать. Не создавать десятки
пустых файлов под каждую комбинацию. Практика VM не подтверждает выбор диска
на физической станции. Все новые непроверенные реализации маркировать
«требует проверки практикой». Собственные скрипты — только по необходимости,
с учётом общих правил репозитория для .ps1/.sh и безопасного журнала ошибок.
